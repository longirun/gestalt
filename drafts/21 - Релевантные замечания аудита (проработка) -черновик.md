## 2. [РЕШЕНО 2026-09-06 → Р35] Контракт запроса read-path (замечание 2.1)

**Проблема (пересобрана с нуля).** Канон определял механизмы поиска — где (scope-видимость, 10 §3.3), как (multi-signal + кривая w, Р27), что возвращаем (Top-K, тишина при слабом сигнале) — но не определял вход: **что является запросом**. Молчаливое «запрос = реплика юзера» проваливается на анафоре/дейксисе («а помнишь ту штуку, о которой спорили во вторник?») и на разрыве форм (сырой разговорный текст vs нормализованное хранилище Р23/Р25) — зеркальный semantic gap write-path, где его закрывает LLM-экстракция. Корень — двусмысленность инварианта Р8: «0 LLM на read-path» читалось и как «движок не вызывает LLM», и как «на пути вообще никого» (тогда сырая реплика — по определению, и плохой поиск — не баг, а спек).

**Решение.**

1. **Оговорка инварианта.** «0 LLM на read-path» = **движок** не вызывает LLM. Формулировка запроса — обязанность потребителя. Двусмысленность снята.
2. **Semantic gap закрывается переносом в уже идущий инференс**, без нового LLM-вызова: хост-агент, отвечающий на реплику, и так проводит инференс и держит диалог в окне — анафора для него разрешена; query formulation едет внутри tool-call. Энд-ту-енд латентность никогда не была ms (хост-LLM сочиняет секунды в любой архитектуре); ms — обещание **подсистемы памяти** (слепок O(1), recall десятки мс) — цело. Минуты Honcho-chat делает не «LLM рядом с read-path», а безграничный LLM-пайплайн в синхронном пути — у нас запрещено контрактом sync-deadline / fail-open (14 §6).
3. **Единый контракт:** `recall(query, [filters])` — один инструмент, одна семантика, без режимов и флагов. Движок всегда детерминированно санитарит вход (лемматизация, стоп-слова, entity-boost по живому словарю Р25): санитария идемпотентна, вытягивает плохой запрос, не вредит хорошему. Продвинутость хоста выражается качеством query, не переключением семантики API. (В3-«режим» из исходной развилки редуцирован: В1-принцип + В2-санитария покрывают всё без третьего состояния.)
4. **Радиус — вариант (а), узкий дефолт.** Дефолт поиска — context(S) (матрица 10 §3.3); USER-радиус (кросс-проектный поиск) — явный параметр. Принцип: **радиус recall ≠ радиус inject** — матрица видимости управляет *неявной* сборкой контекста (инъекция строга: чистота портрета, изоляция), явный поиск может адресовать весь опыт юзера (RLS по user_id — изоляция цела; retrieval по явному запросу — не инъекция). Расширение видимости — всегда явный акт, симметрия no-false-memory. Кросс-проектный лифт Dreaming (10 §4) остаётся про неявный контекст: «как мы делали X в проекте Y» — не юзер-факт о компетенции, в USER не лифтится — только явный поиск.
5. **Структурированные фильтры** рядом с текстом: временной диапазон, радиус (позже домен/вид). «2026» как фильтр надёжнее надежды на эмбеддинг. Механика — temporal query-side (Н5); контракт резервирует поля.
6. **Форма возврата:** Top-K фактов с провенансом (проект-источник, сессия, время) — агенту цитировать («в проекте X мы делали…»); lineage уже на фактах (16 §2.1). Recall по сырым Messages (fallback при тощих фактах) — кандидат v2.
7. **Multi-hop — не движковая фича:** цепочки ссылок («найди решение, принятое после спора с Сашей») = агентная петля tool-call'ов; движок даёт примитивы.
8. **Тишина при слабом сигнале** — пустой результат ниже порога (no-false-memory, 16 §5.2 п.5); порог — ТЗ (Н8).
9. **Классы хостов.** Tool-хост — полноценный recall (function calling — trained-in поведение со структурированным выводом, не prompt-discipline). Inject-хост без tool-loop — слепок + WORLD-хвост в промпт (standing context; per-prompt inject — Н5), запрос ему не нужен. Пайп-хост на сырой реплике — честная тишина; детерминированное разворачивание (окно Messages + rule-based парсер относительных дат + entity-boost словаря) — кандидат v2, требует проверки против буквы Р8 («работа от фактов, не от сырых диалогов»).
10. **Антипаттерны → реестр 12:** безграничный LLM-пайплайн в синхронном пути (Honcho chat: минуты, токены); двухконтрактная дисциплина search/chat (полагание на промпты, которые игнорируются; агент путается в выборе эндпоинта).

**Правило канонического примера (анти-переобучение).** Пример — проверочный сценарий, не источник контракта: контракт выводится из инвариантов, пример валидирует и обнаруживает пробелы. Меняется контракт — сценарии обязаны продолжать проходить; приходит новый сценарий, который контрактом не покрывается — правится контракт (если принцип) или golden-набор (если эмпирика), не гнётся примером.

**Проверочные сценарии:**

- **№1 «jmix» (канонический):** ревью кода в проекте A (диалог на JMix), агент не попал в стиль/архитектуру; реплика «посмотри как мы делали диалог (правила проектирования) в другом проекте в этом году, я не помню название» → агент формулирует `recall("jmix диалог архитектура", {time: 2026, radius: user})` → факты с провенансом проекта B. Валидирует: формулировку агентом (анафора/дейксис разрешены в его окне), content-addressability (название проекта не нужно), темпоральный фильтр, USER-радиус.
- **К1 (пустой результат):** материала нет нигде → тишина, агент честно отвечает «не нашёл» (C-ось, Р14). Контракт обязан специфицировать пути отказа, а не только успех-путь.
- **К2 (без фильтров):** «какие у нас принципы именования миграций?» → дефолт context(S), голый текст: фильтры — опция, не норма.
- **К3 (multi-hop):** цепочка ссылок → агентная петля (п. 7), не движковый траверсал.
- **К4 (портретный запрос):** «в каком стиле писать README?» → отвечает слепок (PREFERENCES/CONSTRUCTS), recall может не зваться: не всё есть recall.

**Правки канона (исполнены):** 14 §6 — абзац контракта запроса; STATUS Р8/Р19 — оговорка «0 LLM = движок». Механика препроцессинга — Н5/ТЗ.

## 3. [РЕШЕНО 2026-09-06 → Р36] Жёсткие детерминированные критерии в метрике (замечание 2.8)

**Проблема.** Рамка метрики заявлена как регресс-тест в CI (11 §3 п.6), но в ней есть единственное звено, где вердикт — *мнение*, а не вычисление: LLM-судья на точках сравнения целых ответов (L2). Следствия: систематический bias (судьи поощряют многословие и вежливость), дрейф вердиктов между версиями судьи (красный CI без реальной поломки), стоимость судейства на каждом прогоне. Опора регресс-теста не должна быть мнением.

**Механика, собранная в проработке (уточняет рамку 11 §3):**

- Точка golden-набора = **материализованный срез**: префикс реального лога, обрезанный в T (срез — конструкция, не параметр) + триггер (реальное сообщение из T) + **истина** (что юзер реально сделал после T) + закодированные проверки. Ответы плеч **не замораживаются** — это выход тестируемой системы; замораживаются материал, истина и проверки.
- «Предсказательная способность» = совпадение ответа агента с **уже записанным** продолжением лога, которое не видит никто из участников (инжест обрезан, промпты чисты). «Экзамен с ответами в сейфе у экзаменатора».
- Прогон = **статистический интеграционный тест**: память поднимается **один раз**, эталонный лог инжестится по хронологии, точки — **чекпоинты** одного replay-прохода (стоп → форс-контуры → плечи → вердикт → докорм лога). Никаких «поднятий × N».
- Ассерт статистический, не булев: гейт = «lift ≥ порог с допуском» (в контуре LLM); булева часть — C-точки (leak = автоматический fail).

**Решение (F1–F4, все «да»).**

- **F1 — детерминированные оракулы, два уровня:** класс проверок с вердиктом без генеративной свободы (обобщение `expect_keywords`). **Veto**: детерминированный провал финален, судья не спасает. **Fast-pass**: точка, решённая оракулами, судьи не требует (экономия токенов, устранение субъективности там, где хватило механики). Судья остаётся только на точках, где оракулы молчат.
- **F2 — природа «детерминированности»:** проверка «противоречит базе» — только по фактам, закодированным в golden-точке (`must`/`must_not`); NLI-классификаторы и прочие модельные суждения — вне класса (вердикт без генеративной свободы — граница класса).
- **F3 — edit-rate — вердикт первого класса на кодовых L2:** в продолжении есть правки юзера → вердикт по фактическому материалу, судья не зовётся. Единственный из оракулов, измеряющий фактическое поведение.
- **F4 — экономика harness'а (без неё CI-гейт нежизнеспособен):**
  - **кэш контрольного плеча B** — B свойство harness'а, не системы под тестом: вход B полностью определён датасетом → генерируется раз на версию (датасет × хост × промпт), замораживается медианный сэмпл; вердикты по-плечевые против истины — методологически чисто, дисперсия сравнения падает;
  - **кэш инжеста** — база фактов чекпоинта материализуется раз на версию Encoding (+ embedding-модель: пороги Р25 привязаны к ней); всё ниже Encoding — слепок/recall/ранжирование — 0 LLM (Р8/Р19), правки там ресторят чекпоинт, replay не платят;
  - **ярусы сьюта:** smoke (20–50 точек, L1+C — оракулы, 0 судей; на каждое изменение пайплайна; дешёвый хост допустим — регрессия относительна) / полный (100–300, судья на L2-остатке, milestone/nightly, боевой хост);
  - **судья-эскалация:** один судья; второй-третий — при споре/неуверенности.

**Позиция в жизненном цикле (ответ на «пиздец как дорого»):** golden — **фаналка на вершине тест-пирамиды**, приёмочный инструмент центрального тезиса («портрет несёт информацию»), не цикл разработки. Цикл разработки — тысячи дешёвых детерминированных unit-тестов ядра (следствие Р8: движок почти весь 0 LLM → unit-testable) + компонентные тесты LLM-границ на центах (маленькие фикстуры экстракции/нейминга/судьи). Порядок: **спайк (Р34) → малый golden-прогон «тезис-чек»** (lift > 0 на 20–50 точках — go/no-go продукта, чтобы не строить башню при нулевом lift) **→ разработка → полный golden-гейт на релизах**.

**Testability-требования (в ТЗ, Н8):** форсируемость контуров (Dreaming/Gestalting/слепок — явный вызов с явным пулом, детерминированный форвард времени); детерминизм replay (фиксированный порядок сообщений и границы батчей); ключи кэшей, пороги допусков, состав ярусов.

**Правки канона (исполнены):** 11 §3 — класс оракулов + каркас/экономика harness'а; golden-формат Р14-в обзаводится полями оракулов (`must`/`must_not`, `choice`, `edits`).

## 5. Рамка спайка (Р34)

**Цель:** верификация базовых гипотез на живом потоке до фиксации требований ТЗ (Н8). Состав среза — кандидат, уточняется при старте спайка:

- **Платформа:** Java 21, zero-dependency core (Р17); Pure PG 16+ / pgvector (Р7).
- **Контуры среза:** Ingest (батчи логов) → **Encoding** (батч-экстракция + двухшаговый дедуп Р23 + канонизаторы object Р25) → таблица `facts` (16 §2.1–2.3) → **PortraitSnapshot** (сборка + инвалидация cutoff + джоба Reconciliation, 14 §4–5) → чтение O(1). Плюс SQL-выражения Δопыт/w (17 §5).
- **Что меряем (эмпирика для ТЗ):** частота split identity и кандидатов склейки на живом словаре; латентность чтения слепка; поведение дедупа на реальных сессиях; токен-стоимость батч-экстракции.
- **Вне среза:** Dreaming/Gestalting (полные), прескриптивы, метрика, RLS/изоляция, WORLD-recall — реализация по ТЗ. Замечание: read-path recall не входит в срез, поэтому проработка §2 спайк не блокирует (ортогональны, можно параллелить).
