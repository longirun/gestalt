# Gestalt — 31: План реализации eval-каркаса (Р45)

> 2026-09-11 · Статус: **рабочий план стадий (временный документ)** · Канон: `docs/spec/28` (Р45) — архитектура, статистика, рамка там; здесь — операционная декомпозиция для разработчика. После завершения тезис-чека документ удаляется или переносится в спеку по решению владельца.

---

## 1. Контекст

Скелет `eval/` существует: Gradle-проект, `EvalConfig` (PG-источник + LLM-роутер), `EvalPoint` (схема точки §3.2 канона), `EvalRunner` (CLI `replay/arms/oracles/report` — заглушки), гигиена VCS. Донор кода — `spike/` (поглощение по §3.1 канона, спайк не трогаем до архивации Р34). Осталось: реализовать шаги каркаса, разметить 20–50 W-точек, прогнать тезис-чек, вынести вердикт.

Порядок из STATUS §3: скелет ✅ → replay → разметка → плечи → оракулы → отчёт → прогон → вердикт → эмпирика в ТЗ (Н8).

Стадии E3–E5 отлаживаются на `dataset/points.example.jsonl` и фикстурах — не ждут готовности живого датасета (E2).

## 2. Решения (рабочие, в развитие Р45)

### 2.1 Хранилище фактов eval

| Вариант | + | − | Вердикт |
|---|---|---|---|
| Отдельная БД `gestalt_eval` на `:5433` | поглощение PG-кода спайка почти без правок; изоляция от `gestalt_spike`; чекпоинты в той же БД | нужен init БД (один раз) | ✅ |
| Файловый стейт в `out/` | нет PG-зависимости | переписывание `FactRepository`/`SchemaMigrator` — дороже поглощения | ✗ |
| Переиспользование `gestalt_spike` | нулевой init | смешивание состояний, инвариант replay («факты только ≤ T») ломается | ✗ |

### 2.2 Кэш дорогих шагов

- **Экстракция (Encoding):** чекпоинт по последней обработанной реплике — в БД `gestalt_eval` (таблица чекпоинтов: сессия → last processed message id). Повторный replay продолжает с чекпоинта, LLM-экстракция обработанных реплик не повторяется (Р36 — кэш инжеста).
- **Плечо B:** файловый кэш в `out/`, ключ = sha256(model + версия промпта + версия датасета + pointId). Смена любого компонента → новая запись, старые не удаляются (аудит заморозки).

### 2.3 Окно видимого контекста

Оба плеча видят одни и те же последние N реплик диалога до T (без будущего). N — параметр конфига, единый для плеч. filler-инвариант Р14 соблюдается на разметке: W-факт точки обязан лежать вне окна (разметчик это проверяет — иначе плечо B выигрывает из контекста).

### 2.4 Формат инъекции плеча A

v1 — сырой JSON PortraitSnapshot отдельной секцией системного промпта. Это первое приближение; эволюция компоновки — по диагнозу §4.3 канона («инъекция не переводится»), не заранее.

### 2.5 Приватность датасета

Рабочий файл разметки — `eval/data/points.live.jsonl` (вне VCS). Путь к датасету — параметр конфига (дефолт `dataset/points.jsonl`). Публикация обезличенного датасета в `dataset/` — отдельное решение после прогона (канон §3.3: коммит только при абсолютной обезличенности).

### 2.6 Тривиальные

- Пакеты копируются из `spike/` как есть (переименование пакета `spike` → `eval`), тесты спайка копируются вместе с классами — приёмочная сетка поглощения.
- Модель плеч может отличаться от модели экстракции — раздельные ключи конфига.
- `FixtureSource` сохраняется (путь к фикстуре — параметр), синтетический экстрактор спайка не копируется: replay без LLM бессмыслен.

## 3. Стадии

### E1. Поглощение + replay

- **Результат:** `./gradlew -p eval run -Pargs=replay` материализует слепки `out/snapshots/<pointId>.json` на момент T для всех точек датасета; повторный прогон не делает LLM-вызовов.
- **Детали:**
  - Копирование из `spike/` в пакет `ru.longirun.gestalt.eval.*`: `ingest/` (MessageSource, HonchoPgSource, FixtureSource, RawMessage, Batcher), `extract/` (ExtractedFact, ExtractionPrompt, FactExtractor, LlmBatchExtractor), `dedup/` (DedupPipeline, ExactMatcher, NearDupMatcher), `portrait/` (SnapshotBuilder, SnapshotStore, ReconciliationJob), `store/` (FactRepository, SchemaMigrator), `llm/` (LlmClient) + тесты.
  - `EvalConfig` расширяется: `target.db.*` (gestalt_eval), `batch.max-messages` / `batch.max-tokens`, `llm.reasoning-effort`, `portrait.owner` / `portrait.project`, `dataset.file`. Имена ключей дублируются в `local.properties.example` (значения — у владельца, вне VCS).
  - Replay: точки группируются по `sourceSession`, сортируются по `sourceMessageId`; один проход по логу (PG `:5433`, read-only): батч → экстракция → дедуп → факты в `gestalt_eval`; при достижении T очередной точки — `ReconciliationJob.reconcile(owner, project)` → слепок в `out/snapshots/<pointId>.json`.
  - Инвариант: в `gestalt_eval` попадают только факты из реплик ≤ текущей T (последовательный проход это гарантирует; перезапуск — продолжение с чекпоинта).
  - Допущение: первый прогон — односессионный срез (параметры сессии/дня — из конфига, как в спайке); мультисессионность — по факту датасета E2.
- **Готово:** replay на живом логе даёт слепки для всех точек; повторный прогон — 0 LLM-вызовов экстракции (по чекпоинту); `./gradlew -p eval assemble` + скопированные тесты зелёные.

### E2. Разметка W-точек (ручная, рабочий стол даёт E1)

- **Результат:** 20–50 точек с проверками; конструируемость зафиксирована; C-точки размечены.
- **Детали:**
  - Шаг `candidates` в runner: выгрузка реплик лога (id, сессия, время, текст) в `eval/data/candidates.jsonl` — для ручного просмотра.
  - Цикл разметки: кандидат → черновик точки (trigger, truth, must/mustNot) → replay материализует слепок на T → W-проверка: в слепке есть факт, релевантный истине? → `coverage` заполняется или точка отсевается с диагнозом уровня (§4.3 канона: лог бедный / Encoding не извлёк / инъекция не переводится — второе проверяется по слепку сразу).
  - C-точки: 5–10 шт., `mustNot` обязателен — маркеры утечки (факты из слепка, которых нет в видимом окне); leak = появление маркера в ответе плеча A.
  - Счётчик конструируемости: просмотренные кандидаты / W-покрытые.
  - Полуавтомат-подсказчик LLM (канон §3.2) — опция, если ручной отбор окажется узким горлом.
- **Готовно:** `points.live.jsonl` содержит 20–50 точек (L1 W-покрытые + C); каждая L1-точка имеет непустой `coverage`; must/mustNot машинно проверяемы (сверка вручную по выборке).

### E3. Плечи A/B

- **Результат:** `./gradlew -p eval run -Pargs=arms` прогоняет оба плеча на всех точках; ответы в `out/answers/<pointId>.{a,b}.json`; плечо B заморожено кэшем.
- **Детали:**
  - Промпт-сборка: общий системный промпт (версия — в конфиге, входит в кэш-ключ B) + окно истории (N реплик до T, §2.3) + триггер. Плечо A: + секция-инъекция слепка из `out/snapshots/<pointId>.json` (§2.4). Плечо B: без секции.
  - Хост: `LlmClient` на внешний OpenAI-совместимый роутер, temperature 0, одна модель в обоих плечах (конфиг `arms.model`).
  - Кэш B по §2.2; ответы сохраняются с метаданными (модель, токены, латентность).
  - Экономика: 2 вызова на точку без кэша (A + B), повторные прогоны — только A.
- **Готовно:** прогон arms на example-точках (отладка) и на живом датасете; повторный прогон плеча B — 0 LLM-вызовов; assemble зелёный.

### E4. Оракулы

- **Результат:** `./gradlew -p eval run -Pargs=oracles` выдаёт вердикты по точкам: A pass/fail, B pass/fail, C-гейт.
- **Детали:**
  - must/must_not: нормализованное вхождение (lowercase, ё→е, trim) — все must присутствуют, ни один mustNot не присутствует.
  - edit-rate (кодовые точки): токенное расстояние Левенштейна между ответом и истиной, rate = dist / max(len); схема точки расширяется nullable-полем порога (`maxEditRate`) — текущая схема `EvalPoint` его не имеет.
  - C-точки: leak = любой mustNot-маркер в ответе плеча A → veto всего прогона (провал прогона, lift не читается; канон §4.5).
  - Выход: `out/oracles.jsonl` — по точке вердикты обоих плеч + leak-флаги.
- **Готовно:** оракулы детерминированы (повторный прогон на тех же ответах — тот же результат); ручная сверка выборки точек; assemble зелёный.

### E5. Отчёт + статистика

- **Результат:** `./gradlew -p eval run -Pargs=report` строит `out/report.md`: lift на решённых парах, значимость, posterior, конструируемость, C-гейт, вердикт.
- **Детали:**
  - Решённые пары: (A pass, B fail) = побед A; (A fail, B pass) = побед B; ничьи вне выборки.
  - Точный односторонний знаковый тест: p = P(Bin(побед A + побед B, 0.5) ≥ побед A); go при p ≤ 0.05. Референс мощности (канон §4.1): 20 решённых → 15 побед A; 30 → 20; 50 → 32 — таблица в отчёт.
  - Posterior: Beta(1 + побед A, 1 + побед B) → P(A > B) — руль добора.
  - Конструируемость: доля W-точек среди просмотренных кандидатов (из журнала E2).
  - C-гейт: булев, veto — независимо от lift.
  - Вердикты: go / insufficient (добор) / no-go условный (с уровнем §4.3).
  - Протокол прогона (пре-регистрация): `dataset/protocol.md` — тест, α, правило ничьих, правило остановки — коммитится ДО первого живого прогона (git-история = регистрация).
- **Готовно:** report из артефактов E3/E4 без LLM-вызовов; на example-точках — самосогласован (ручная проверка арифметики на маленьком примере).

### E6. Прогон тезис-чека + вердикт + эмпирика (Н8)

- **Результат:** вердикт по тезису зафиксирован; эмпирика передана в ТЗ; реестр обновлён.
- **Детали:**
  - Полный цикл на живом датасете: replay → arms → oracles → report; повторные прогоны (≥ 2–3, дешёвые: кэш B, чекпоинты) — вердикт по стабилизировавшейся картине (канон §4.5).
  - Итоги — `docs/research/26` (по образцу research/25): числа, вердикт с границами валидности (доказательство существования, не калибровка), диагноз уровней при недоборе.
  - Эмпирика → Н8: конструируемость, шум L2, поведение C-точек, дефолты порогов.
  - STATUS §3 / ROADMAP / CHANGELOG — обновить; судьба этого документа (удалить/перенести) — решение владельца.
- **Готовно:** research-заметка закоммичена; STATUS отражает вердикт.
