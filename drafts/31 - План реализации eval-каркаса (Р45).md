# Gestalt — 31: План реализации eval-каркаса (Р45)

> 2026-09-11 · Статус: **рабочий план стадий (временный документ)** · Канон: `docs/spec/eval/28` (Р45) — архитектура, статистика, рамка там; здесь — операционная декомпозиция для разработчика. После завершения тезис-чека документ удаляется или переносится в спеку по решению владельца.

## 1. Контекст

Скелет `eval/` существует: Gradle-проект, `EvalConfig` (PG-источник + LLM-роутер), `EvalPoint` (схема точки §3.2 канона), `EvalRunner` (CLI `replay/arms/oracles/report` — заглушки), гигиена VCS. Донор кода — `spike/` (поглощение по §3.1 канона, спайк не трогаем до архивации Р34). Осталось: реализовать шаги каркаса, разметить 20–50 W-точек, прогнать тезис-чек, вынести вердикт.

Порядок из STATUS §3: скелет ✅ → replay → разметка → плечи → оракулы → отчёт → прогон → вердикт → эмпирика в ТЗ (Н8).

Стадии E3–E5 отлаживаются на `dataset/points.lme.jsonl` (E2-PC, positive control) и фикстурах — не ждут готовности живого датасета (E2).

## 2. Решения (рабочие, в развитие Р45)

### 2.1 Хранилище фактов eval

| Вариант | + | − | Вердикт |
|---|---|---|---|
| Отдельная БД `gestalt_eval` на `:5433` | поглощение PG-кода спайка почти без правок; изоляция от `gestalt_spike`; чекпоинты в той же БД | нужен init БД (один раз) | ✅ |
| Файловый стейт в `out/` | нет PG-зависимости | переписывание `FactRepository`/`SchemaMigrator` — дороже поглощения | ✗ |
| Переиспользование `gestalt_spike` | нулевой init | смешивание состояний, инвариант replay («факты только ≤ T») ломается | ✗ |

### 2.2 Кэш дорогих шагов

- **Экстракция (Encoding):** чекпоинт по последней обработанной реплике — в БД `gestalt_eval` (таблица чекпоинтов: сессия → last processed message id). Повторный replay продолжает с чекпоинта, LLM-экстракция обработанных реплик не повторяется (Р36 — кэш инжеста).
- **Плечо B:** файловый кэш в `out/`, ключ = sha256(model + версия промпта + версия датасета + pointId). Смена любого компонента → новая запись, старые не удаляются (аудит заморозки).

### 2.3 Окно видимого контекста

Оба плеча видят одни и те же последние N реплик диалога до T (без будущего). N — параметр конфига, единый для плеч. filler-инвариант Р14 соблюдается на разметке: W-факт точки обязан лежать вне окна — в механике разметки «с конца» (§2.9) проверка автоматическая (рождение факта-покрытия ≤ window_start), не руками разметчика.

### 2.4 Формат инъекции плеча A

v1 — сырой JSON PortraitSnapshot отдельной секцией системного промпта. Это первое приближение; эволюция компоновки — по диагнозу §4.3 канона («инъекция не переводится»), не заранее.

### 2.5 Приватность датасета

Рабочий файл разметки — `eval/data/points.live.jsonl` (вне VCS). Путь к датасету — параметр конфига (дефолт `dataset/points.jsonl`). Публикация обезличенного датасета в `dataset/` — отдельное решение после прогона (канон §3.3: коммит только при абсолютной обезличенности).

Решение E2: и L1, и C-точки размечаются из одной сессии; T-день — последний полноценный день диалога (см. уточнения ниже).

### 2.7 Оснастка разметчика (E2) — viewer-тест

Рабочий стол разметчика — `EvalViewerTest` в test-source-set: JUnit-тест поднимает JDK `HttpServer` (static index.html + API-ручки), разметчик работает в браузере, стоп теста в IDE = стоп сервера. Обоснование: жизненный цикл сервера = сессия разметки; UI-код не пачкает main (eval — измерительный инструмент, не продукт); запуск одной кнопкой из IDE. Тест помечен тегом `viewer` и исключён из дефолтного `gradlew test` (иначе билд зависнет на блокирующем ожидании).

- Чтение с диска на каждый GET (день, points-файл `dataset.file`, слепки, журнал, wcheck) — F5 в браузере подхватывает правки файлов и новые слепки без рестарта.
- **День viewer'а (LME, 2026-09-12):** `GET /api/day` строится по точкам датасета — LME-сессии получают лог из LongMemEval-файла (`source.lme.file`, один streaming-проход; нумерация реплик та же, что у replay/wcheck — контракт `LongMemEvalAdapter.buildLog`), live-сессии — из `data/candidates.jsonl`. Ключ реплики в UI — пара `(session, id)`: LME-сессии нумеруют реплики каждая с единицы, глобальный id неоднозначен; окно/префикс/будущее режутся внутри сессии точки. Production-факты для чистого LME-датасета не запрашиваются (микромиры в production не инжестятся).
- Запись — только append (POST `/api/point`, `/api/journal`); правка существующих точек — руками в IDE.
- Production-факты (gestalt_spike, read-only, `GET /api/prod-facts`): выводы, уже лежащие в базе, с evidence — из каких реплик среза выведен каждый факт; креды `prod.db.*` в local.properties (gestalt_ro, GRANT SELECT).
- **Экран (перевёрнут в точка-центричный, 2026-09-11):** основная задача вьювера — показать точки, лог — вторичен. Дефолтный режим «точки»: слева список точек (L1 / C / отсеянные кандидаты — отрицательные досье с причиной и расшифровкой; статусы W ✔/✘/~ и A/B в строке), справа **досье точки** — единая история сверху вниз: (1) таймлайн `префикс (знание вне окна) → W0 → окно (W0, M) — видят плечи → M — развилка/триггер → будущее — истина` с бейджами evidence валидных фактов и эвристикой выводимости по must-маркерам (подстрока ≠ знание — подсказка шага «выводимость» §2.9, решение за разметчиком); (2) «почему выбрана/отсеяна»: pattern → W-проверка (covered/not + valid/in-window/lag/unknown) → журнал-вердикт с расшифровкой причин; (3) «какой контекст помогает»: coverage точки + валидные факты-покрытия (клик — coverage-строка в буфер, правка точки осталась руками в jsonl) с классификацией max evidence ≤ W0; (4) «правильный ответ»: truth + must/mustNot-чипы; (5) **A/B**: карточки плеч (ответ A с инъекцией vs B-контроль, вердикты оракулов pass/fail, пропущенные must, решённая пара / вклад в lift, C-leak veto), свёрнутый слепок-инъекция плеча A с подсветкой «слова истины × факты»; production-выводы, форма разметки и вердикт-кнопки — свёрнутые секции того же досье. Режим «лог разметки»: реплики среза с бейджами (точка/вердикт/«база» на evidence) для поиска кандидатов «с конца» → то же досье кандидата.
- **Контракт данных A/B (обязателен для E3/E4):** `out/answers/<pointId>.{a,b}.json` — `{answer, model, tokens, latencyMs, cached, at}`; `out/oracles.jsonl` — по строке на точку `{pointId, level, a: {pass, matchedMust[], missedMust[], matchedMustNot[]}, b: {…}, leak, leakMarkers[]}`. Решённость пары и победитель viewer выводит сам из `a.pass/b.pass` (A pass & B fail = победа A). Ручки: `GET /api/answers` (агрегат `{pointId: {a, b}}`, битые файлы молча пропускаются), `GET /api/oracles` (jsonl с диска).

### 2.8 Журнал разметки (E2)

`eval/data/marking-journal.jsonl` (вне VCS): по одному просмотренному кандидату запись `{candidateId, verdict: taken|rejected, reason: poor-log|no-fork|in-window|encoding|noise|null, pointId?, at}` (причины расширены правкой §2.9). Потребитель — E5: конструируемость = taken / (taken + rejected), диагнозы уровней §4.3 канона. Схема точки/журнала поддерживается viewer'ом (§2.7), вручную журнал не ведётся.

### 2.9 Разметка «с конца»: паттерн → развилка (E2, правка по факту живого прогона)

Диаграммы: `docs/spec/eval/таймлайн-точки.puml`, `docs/spec/eval/разметка-точек.puml`, `docs/spec/eval/прогон-плечей.puml`.

Разворот направления разметки: не «от реплики к будущему», а «от паттерна к развилке». Основание: на живом логе большинство реплик информационные («какая ты модель?») — «будущее» для них не определено, определение точки «истина = следующая реплика» работает только для decision-forks; разметка «вперёд» перегружает разметчика. Новый критерий точки: **точка существует только там, где хороший ответ на триггер зависит от знания о юзере/проекте**; вопросы про мир — не точки (плеча ответят одинаково, памяти неоткуда помочь).

Четыре шага: (1) **паттерн** — факт/предпочтение/поведение, наблюдаемое в конце лога; (2) **выводимость** — выводим ли паттерн из префикса лога до его проявления (человек; нет → poor-log); (3) **развилка** — реальная реплика-развилка M, где знание паттерна меняет ответ (нет → no-fork); рождение факта в памяти ищется автоматически diff'ом слепков (факты монотонны — только добавляются), не человеком; (4) **прогон** — существующие плечи A/B + оракулы; пайплайну E3–E5 всё равно, как нашли точку.

**Связка позиций (решение по открытому вопросу):** точка прогона = **M** — триггер = реальная реплика у M, слепок на M, окно = N реплик до M. Рождение факта T (первый слепок с фактом) — служебная метрика прогнозной дистанции T→M (эмпирика Н8, нижняя оценка по сетке слепков), не позиция прогона. Развязка запрещена: слепок всегда в позиции триггера — заморозка слепка на T при позднем триггере занижала бы плечо A против прод-семантики «память состояния момента ответа».

**Граница слепка vs окна (filler-инвариант Р14 в новой механике):** слепок строится **строго до триггера** (M exclusive) — в момент среза триггерная реплика ещё не прошла экстракцию; семантика «память момента ответа» (сначала ответь, потом перевари). Мотивация: экстракция триггера не даёт плечу A новой информации (триггер видят оба дословно), но dedup/reconcile по тексту вопроса может возмутить другие факты портрета — дельта A/B измеряла бы чувствительность экстракции, а не пользу памяти. Реплики окна (W0, M) обрабатываются в портрет как обычно — дублирование видимого обеими сторонами, не асимметрия; конфликтные случаи (17546-класс) — материал диагноза §4.3. Extract-from-query-then-answer — отдельный режим, не в этом eval. Валидность точки управляется не слепком, а происхождением факта-покрытия: **max evidence-id факта ≤ W0**, где **W0 = window_start(M) = последняя реплика вне окна** — реплика непосредственно перед окном (evidence-атрибуция экстрактора — принятая аппроксимация; рождение из W0 — вне видимости плеча B, честная работа памяти). Вердикты по evidence факта из слепка M: max ≤ W0 → valid; рождение > W0 → in-window reject (плечо B видит происхождение в окне); рождение ≤ W0 < последний reinforcement → lag, не valid (повтор из окна раскрывает факт плечу B — присутствие в слепке W0 не спасает); пустой evidence → unknown, не valid. Точка covered ⇔ есть хотя бы один valid-факт-кандидат. Слепок W0 в проверке не участвует — аудит-след сетки (факт материализовался в срезе ≤ W0); факт в слепке W0 с пустым evidence всё равно unknown (неизвестно, был ли reinforcement в окне).

**Сетка материализации:** без плотной сетки и бисекции — дорого (первый живой прогон: 16 LLM-вызовов ≈ 44k токенов на 3 слепка). Два проба на L1-точку: M (прогон) и W0 (валидность). Если cursor replay уже за W0 (соседние точки ближе N) — evidence ближайшего доступного слепка ≤ W0; нет слепка — точка откладывается (insufficient grid), не reject.

### 2.10 Методология отбора точек (решение 2026-09-12, отложено до E2-PC)

Диагноз тупика E2: §2.9 определяет проверку кандидата (паттерн → выводимость → развилка), но не порождение и отбор — процесс наитийный, невоспроизводим; провал jrestly (7 точек одной оси «публикация библиотеки») — не беда лога, а непроверенное покрытие осей (construct underrepresentation, Messick).

Формализация отбора = пять вопросов: **(Q1)** критерий принадлежности — есть (§2.9); **(Q2)** структура популяции — решётка категорий знания × развилок; **(Q3)** перечисление кандидатов — generator (recall-слой, к точности требований не несёт); **(Q4)** суждение о принадлежности — кодбук критериев inclusion/exclusion (precision-слой, воспроизводим; журнал §2.8 — готовый screening-flow по образцу PRISMA); **(Q5)** достаточность — мощность §4.1 канона для тезис-чека (целевая выборка), вероятностная выборка — полный ярус. Опоры: ECD/blueprint (Mislevy), validity (Messick), LongMemEval/LOCOMO (генерация → автофильтр → adjudication), Patton purposeful sampling, IRT item analysis.

Решения: (1) решётка выводится **индуктивно** — открытым кодированием материала среза (живой рабочий проект), не дедуктивно из теории портрета; тонности честной индукции: единица кодирования шире «есть развилка» (иначе решётка смещена к уже умеемому), категории называет человек — LLM максимум generator/второй кодировщик (иначе скрытая дедукция из его априоров); (2) пайплайн: эпизодник (LLM-фильтр реплик с решениями/предпочтениями) → открытое кодирование до сатурации (2–3 дня без новых категорий) → кодбук (пре-регистрация до разметки) → квоты по решётке (каждая категория ≥ 1 точки) → разметка по §2.9 → item analysis по категориям после пилота ~10 точек; (3) роли разделены: generator ≠ adjudicator — «накидал 10 точек по убеждениям» уходит: решётка показывает покрытие, кодбук — вердикт, мощность — стоп. Статус: отложено — сначала калибровка каркаса (E2-PC).

## 3. Стадии

### E1. Поглощение + replay ✅

- **Результат:** `./gradlew -p eval run -Pargs=replay` материализует слепки `out/snapshots/<pointId>.json` на момент T для всех точек датасета; повторный прогон не делает LLM-вызовов.
- **Детали:**
  - Копирование из `spike/` в пакет `ru.longirun.gestalt.eval.*`: `ingest/` (MessageSource, HonchoPgSource, FixtureSource, RawMessage, Batcher), `extract/` (ExtractedFact, ExtractionPrompt, FactExtractor, LlmBatchExtractor), `dedup/` (DedupPipeline, ExactMatcher, NearDupMatcher), `portrait/` (SnapshotBuilder, SnapshotStore, ReconciliationJob), `store/` (FactRepository, SchemaMigrator), `llm/` (LlmClient) + тесты.
  - `EvalConfig` расширяется: `target.db.*` (gestalt_eval), `batch.max-messages` / `batch.max-tokens`, `llm.reasoning-effort`, `portrait.owner` / `portrait.project`, `dataset.file`. Имена ключей дублируются в `local.properties.example` (значения — у владельца, вне VCS).
  - Replay: точки группируются по `sourceSession`, сортируются по `sourceMessageId`; один проход по логу (PG `:5433`, read-only): батч → экстракция → дедуп → факты в `gestalt_eval`; при достижении T очередной точки — `ReconciliationJob.reconcile(owner, project)` → слепок в `out/snapshots/<pointId>.json`.
  - Инвариант: в `gestalt_eval` попадают только факты из реплик ≤ текущей T (последовательный проход это гарантирует; перезапуск — продолжение с чекпоинта).
  - Допущение: первый прогон — односессионный срез (параметры сессии/дня — из конфига, как в спайке); мультисессионность — по факту датасета E2.
- **Готовность:** replay на живом логе даёт слепки для всех точек; повторный прогон — 0 LLM-вызовов экстракции (по чекпоинту); `./gradlew -p eval assemble` + скопированные тесты зелёные.

### E2-PC. Positive control на LongMemEval (решение 2026-09-12)

- **Результат:** каркас (replay → wcheck; далее arms/oracles/report на тех же точках) прогнан на внешнем бенчмарке: слепки материализуются, W-покрытие gt-ответов проверяется; цепь Encoding→слепок подтверждена на чужом материале.
- **Обоснование (метрология):** калибровочный образец с известным ответом до дорогой живой разметки — без него lift=0 живого прогона неотличим от поломки каркаса. Побочно: первый кусок Р37 (внешние бенчмарки на том же каркасе) и референс чужой решётки (таксономия LongMemEval) перед индуктивным кодбуком §2.10.
- **Детали:**
  - Источник: LongMemEval (HF `xiaowu0162/longmemeval`), oracle-подвыборка (медиана 23 реплики/вопрос — дешёвый инжест; полный haystack s-версии — при необходимости); стартовая категория `single-session-user` (короткие фактические ответы — ближайший аналог W-точек о юзере), ~30 точек; файлы в `eval/data/lme/` (вне VCS).
  - Точка: вопрос = реплика-вопрос в конце лога (M), слепок M-exclusive сохраняет инвариант (вопрос не инжестится); истина = gt-ответ бенчмарка, must = ответ (отсев: невекстовые ответы и > 8 слов — must-вхождение нестрого).
  - Изоляция: `sourceSession = lme-<question_id>` = портрет-проект вопроса, владелец синтетический `user:lme-<question_id>` — USER-scope факты шарятся между проектами одного владельца (Р19, `findByOwnerAndProject`: `scope='USER' OR project_id=?`), без синтетического владельца живые USER-факты протекают в слепки positive control'а (найдено 2026-09-12 на smoke: 59 живых фактов в слепке); слепки вопросов не смешиваются; конфиг `source.lme.file`; шаг CLI `lme [types] [limit]` генерит `dataset/points.lme.jsonl`; сессии лога упорядочены по датам, вопрос — последняя реплика.
  - Границы валидности: тезис-чеком НЕ является (истина = gt-ответ, не будущее лога; механика развилок §2.9 не воспроизводится); категория abstention в релизе отсутствует → C-точек нет, контроль молчания (Р14) остаётся за живым датасетом.
- **Готовность:** `points.lme.jsonl` + слепки для всех точек + wcheck covered на большинстве IE-точек (Encoding извлекает факты-ответы); assemble зелёный.

### E2. Разметка W-точек (с конца: паттерн → развилка — §2.9)

- **Результат:** 20–50 точек с проверками; конструируемость зафиксирована; C-точки размечены.
- **Детали:**
  - Шаг `candidates`/viewer (§2.7) — рабочий материал: реплики среза с позициями; разметка стартует с хвоста лога (паттерны конца), не с произвольных реплик.
  - Цикл разметки (§2.9): паттерн → выводимость из префикса (человек) → развилка M + триггер → W-проверка автоматическая: факт-паттерн в слепке на M? рождение по evidence вне окна? → билет или reject с причиной в журнале (§2.8).
  - Билет: `pattern` (какое знание тестируем) — новое поле схемы точки; `truth` — реальное продолжение лога (не меняется — объективность оракулов); `coverage` рождается из diff'а автоматически (факт + слепок первого появления), человек валидирует релевантность паттерну. Конфликтное покрытие (факт слепка противоречит истине — кейс L1-17546 «prefers DEBUG» vs «оставляем info») НЕ отсекается: релевантность ≠ корректность, плечо A проигрывает такое честно → диагноз §4.3; конфликт помечается в журнале.
  - Replay доработка: два проба на L1-точку (M и W0, §2.9) — внутри точки порядок инжеста `(cursor → W0] → слепок W0 → (W0 → M) → слепок M` — срез M строго до обработки триггерной реплики, §2.9; инвариант «факты ≤ T» (E1) уже охраняет порядок; insufficient grid — отложить точку, не reject.
  - C-точки: 5–10 шт., `mustNot` обязателен — маркеры утечки (факты из слепка, которых нет в видимом окне); leak = появление маркера в ответе плеча A — без изменений.
  - Счётчик конструируемости: taken / (taken + rejected) по журналу; причины reject маппятся на §4.3 канона (poor-log → лог бедный; encoding → Encoding не извлёк; no-fork / in-window — не диагноз системы, идут только в конструируемость).
  - Полуавтомат-подсказчик LLM (канон §3.2) — опция, если ручной отбор окажется узким горлом.
  - Черновики первого живого прогона (L1-17513/17533/17546) перевердиктируются по новым правилам: 17513 — кандидат poor-log (решение не подкреплено логом до T), 17546 — W-точка с конфликтным покрытием (взять, пометив конфликт), 17533 — по факту.
- **Готовность:** `points.live.jsonl` содержит 20–50 точек (L1 W-покрытые + C); для каждой L1-точки есть слепки M и W0-evidence (или явный insufficient grid); каждая L1-точка имеет `pattern` и автоматически порождённый `coverage`; журнал ведётся viewer'ом; must/mustNot машинно проверяемы (сверка вручную по выборке).

### E3. Плечи A/B

- **Результат:** `./gradlew -p eval run -Pargs=arms` прогоняет оба плеча на всех точках; ответы в `out/answers/<pointId>.{a,b}.json`; плечо B заморожено кэшем.
- **Детали:**
  - Промпт-сборка: общий системный промпт (версия — в конфиге, входит в кэш-ключ B) + окно истории (N реплик до T, §2.3) + триггер. Плечо A: + секция-инъекция слепка из `out/snapshots/<pointId>.json` (§2.4). Плечо B: без секции.
  - Хост: `LlmClient` на внешний OpenAI-совместимый роутер, temperature 0, одна модель в обоих плечах (конфиг `arms.model`).
  - Кэш B по §2.2; ответы сохраняются с метаданными (модель, токены, латентность).
  - Экономика: 2 вызова на точку без кэша (A + B), повторные прогоны — только A.
- **Готовность:** прогон arms на example-точках (отладка) и на живом датасете; повторный прогон плеча B — 0 LLM-вызовов; assemble зелёный.

### E4. Оракулы

- **Результат:** `./gradlew -p eval run -Pargs=oracles` выдаёт вердикты по точкам: A pass/fail, B pass/fail, C-гейт.
- **Детали:**
  - must/must_not: нормализованное вхождение (lowercase, ё→е, trim) — все must присутствуют, ни один mustNot не присутствует.
  - edit-rate (кодовые точки): токенное расстояние Левенштейна между ответом и истиной, rate = dist / max(len); схема точки расширяется nullable-полем порога (`maxEditRate`) — текущая схема `EvalPoint` его не имеет.
  - C-точки: leak = любой mustNot-маркер в ответе плеча A → veto всего прогона (провал прогона, lift не читается; канон §4.5).
  - Выход: `out/oracles.jsonl` — по точке вердикты обоих плеч + leak-флаги.
- **Готовность:** оракулы детерминированы (повторный прогон на тех же ответах — тот же результат); ручная сверка выборки точек; assemble зелёный.

### E5. Отчёт + статистика

- **Результат:** `./gradlew -p eval run -Pargs=report` строит `out/report.md`: lift на решённых парах, значимость, posterior, конструируемость, C-гейт, вердикт.
- **Детали:**
  - Решённые пары: (A pass, B fail) = побед A; (A fail, B pass) = побед B; ничьи вне выборки.
  - Точный односторонний знаковый тест: p = P(Bin(побед A + побед B, 0.5) ≥ побед A); go при p ≤ 0.05. Референс мощности (канон §4.1): 20 решённых → 15 побед A; 30 → 20; 50 → 32 — таблица в отчёт.
  - Posterior: Beta(1 + побед A, 1 + побед B) → P(A > B) — руль добора.
  - Конструируемость: доля W-точек среди просмотренных кандидатов (из журнала E2).
  - C-гейт: булев, veto — независимо от lift.
  - Вердикты: go / insufficient (добор) / no-go условный (с уровнем §4.3).
  - Протокол прогона (пре-регистрация): `dataset/protocol.md` — тест, α, правило ничьих, правило остановки — коммитится ДО первого живого прогона (git-история = регистрация).
- **Готовность:** report из артефактов E3/E4 без LLM-вызовов; на example-точках — самосогласован (ручная проверка арифметики на маленьком примере).

### E6. Прогон тезис-чека + вердикт + эмпирика (Н8)

- **Результат:** вердикт по тезису зафиксирован; эмпирика передана в ТЗ; реестр обновлён.
- **Детали:**
  - Полный цикл на живом датасете: replay → arms → oracles → report; повторные прогоны (≥ 2–3, дешёвые: кэш B, чекпоинты) — вердикт по стабилизировавшейся картине (канон §4.5).
  - Итоги — `docs/research/26` (по образцу research/25): числа, вердикт с границами валидности (доказательство существования, не калибровка), диагноз уровней при недоборе.
  - Эмпирика → Н8: конструируемость, шум L2, поведение C-точек, дефолты порогов.
  - STATUS §3 / ROADMAP / CHANGELOG — обновить; судьба этого документа (удалить/перенести) — решение владельца.
- **Готовность:** research-заметка закоммичена; STATUS отражает вердикт.
