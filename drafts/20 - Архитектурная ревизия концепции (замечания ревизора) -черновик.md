## 1. Резюме ревизии

Концептуально проект выглядит как академический труд: Тульвинг, Бартлетт, Келли, Снодграсс, Пиаже, Андервуд, Викстед. Выстроена стройная философская система категорий (WORLD vs PSYCHE, Axis vs Instance, триада процессов, опытное время).

Однако при взгляде на систему как на **инженерный сервис** проявляется синдром «архитектурного астронавта»:
- Попытка решить проблему недетерминизма LLM чисто детерминированными реляционными методами там, где они бессильны.
- Перекладывание на тяжелые асинхронные джобы того, что ломает рантайм здесь и сейчас.
- Гипертрофия теоретической надстройки при полном отсутствии проверки боем на реальном коде.

## 2. Критические замечания и архитектурные уязвимости

### 2.1. Иллюзия «0 LLM на Read-Path» и семантическая слепота
* **Где зафиксировано:** Р8, Р19, `14 §6`, `16 §5`.
* **Суть проблемы:** 
  Постулируется детерминированное чтение без LLM: $O(1)$ слепок `PortraitSnapshot` + Top-K по HNSW/FTS для `WORLD`-фактов. 
  В реальном интерактивном диалоге пользователь не формулирует запросы в терминах сущностей базы. Он пишет: *«Слушай, а помнишь ту штуку, о которой мы спорили в прошлый вторник? Давай переделаем по второму варианту»*.
* **Где сломается:**
  1. Эмбеддинг сырого разговорного сообщения пользователя в косинусном поиске по `statement` фактов дает низкую точность (Semantic Drift / Query Mismatch).
  2. Полнотекстовый поиск (`tsvector`) по сырой реплике поднимет стоп-слова или ничего не найдет из-за отсутствия точных лексем.
  3. Без **Query Rewriting / Query Expansion** на горячем пути агент получит случайный или зашумленный контекст. Принесение семантической точности в жертву ради $O(1)$-скорости делает компонент `WORLD-recall` в v1 ненадежным.
* **К проработке:** 
  Признать необходимость легковесного шага нормализации запроса (Query Preprocessing) или четко специфицировать fallback-механику ContextProducer (Н5).

### 2.2. Фикция детерминированного exact-дедупа (0 LLM) на Fast-Path
* **Где зафиксировано:** Р6, Р23, `16 §4.1`.
* **Суть проблемы:**
  Дедупликация STATE-фактов объявлена детерминированной: поиск по составному ключу `identity = (owner, scope, project, subject_norm, predicate_norm, conditions)`. Если совпало — инкремент `reinforcement_count`; если отличается `object` — кандидат в supersession.
  Но LLM — генеративная модель, а не конечный автомат. Даже при подаче словаря в extraction-промпт (Р25):
  * Сессия 1: юзер говорит *«порт базы 5432»*. Экстрактор вернул `subject: "postgres"`, `predicate: "port"`.
  * Сессия 2: юзер говорит *«перевесил бд на 5433»*. Экстрактор вернул `subject: "database"`, `predicate: "listen_port"`.
* **Где сломается:**
  1. `identity-lookup` дает промах.
  2. Факт воспринимается как новый. Механизм supersession не активируется.
  3. В базе параллельно живут два активных противоречащих факта: `postgres.port = 5432` и `database.listen_port = 5433`.
  4. Фоновая консолидация словарей (Reconciliation) склеит их через триграммы/косинус/судью лишь спустя часы или дни. В течение всего этого окна агент оперирует разорванным контекстом. На малых объемах данных (молодой проект) fingerprint ко-использования по Жаккару не соберет статистику для склейки.
* **К проработке:**
  Ввести быстрый эвристический или семантический fallback дедупликации на Fast-Path до создания нового факта, либо минимизировать зависимость тождественности от свободного наименования предикатов.

### 2.3. Гонки данных и блокировки в конвейере памяти
* **Где зафиксировано:** Р6, Р10, Р19, `14 §5`, `16 §2.3`, `16 §3.1`.
* **Суть проблемы:**
  Конкурентная среда с Project Loom, воркерами Encoding, фоновым Dreaming, свипами Reconciliation и синхронным fallback читателя:
* **Где сломается:**
  1. **Encoding vs Dreaming (гонка строки):** Воркер Encoding делает `UPDATE facts SET reinforcement_count = reinforcement_count + 1, last_seen_at = now() WHERE id = ...`. Одновременно Dreaming помечает этот же факт как `SUPERSEDED`. При `READ COMMITTED` транзакция Encoding рискует обновить `last_seen_at` у архивной строки, сделав ее по таймстампу «новее» актуального преемника, либо перезатереть статус.
  2. **Коллизия частичного уникального индекса:** Инвариант `UNIQUE(identity) WHERE status = 'ACTIVE'`. При параллельной обработке пачки сообщений два воркера могут одновременно попытаться вставить один и тот же новый факт. Один из них упадет с ошибкой нарушения уникальности. Требуется явный протокол `INSERT ... ON CONFLICT` с повторной проверкой состояния.
  3. **Snapshot Stampede:** Читателю разрешено синхронно пересобирать слепок при отставании фоновой джобы (`stale(profile) : max(system_time) > cutoff`). Если от пользователя приходит несколько параллельных агентских запросов, все потоки одновременно увидят флаг устаревания и начнут параллельно пересчитывать один и тот же слепок.
* **К проработке:**
  Заложить single-flight / распределенный мьютекс на пересборку слепка и спроектировать строгие идемпотентные SQL-транзакции для параллельного приёма.

### 2.4. Догматизм «Опытного времени» (интерференция без календаря)
* **Где зафиксировано:** Р27, Р28, `17 §2`.
* **Суть проблемы:**
  Календарное время полностью выведено из динамики памяти: затухание ($w$) рассчитывается исключительно от накопленных сессий интерференционного пула ($\Delta\text{опыт}$). Метафора взята из экспериментов Андервуда (1957) над заучиванием слогов.
* **Где сломается:**
  1. **Парадокс замороженного проекта:** Пользователь отработал 50 сессий в Проекте А (Java 21), затем ушел на 2 года в Проект Б (провел там 1000 сессий). В Проекте А сессий не было. По возвращении в Проект А $\Delta\text{опыт} = 0$, и система считает двухлетние факты 100% свежими ($w = 1.0$), хотя мир изменился, библиотеки устарели, а API умерли.
  2. **Парадокс отладочного спринта:** Интенсивный вечер отладки сложного бага порождает 40 коротких сессий. Поскольку единица опыта — сессия, $\Delta\text{опыт} = 40 \gg H$. Фундаментальные архитектурные решения, принятые два дня назад, резко затухают к несгораемому минимуму $w_{floor}$ просто из-за частого перезапуска контекста.
* **К проработке:**
  Вернуть гибридный учет времени: опытная интерференция как основной вес + мягкий календарный полураспад как защита от энтропии внешнего мира (особенно для домена `WORLD`).

### 2.5. Реляционная шизофрения: Recursive CTE vs денормализованные массивы
* **Где зафиксировано:** Р7 vs `16 §2.1`, `09 §3`.
* **Суть проблемы:**
  Решение Р7 обещает графовые обходы через «таблицы рёбер + recursive CTE». При этом в канонических схемах объявлены денормализованные массивы: `lineage: [UUID]`, `generalized_from: [UUID]`, `evidence: [Fact/PSYCHE]`.
* **Где сломается:**
  1. На массивах `UUID[]` невозможно повесить Foreign Key constraints. Ссылочная целостность в PostgreSQL отсутствует: удаление или миграция сущности порождает битые ссылки.
  2. Рекурсивные CTE через `JOIN ... ON target.id = ANY(source.lineage)` плохо поддаются оптимизации планировщиком Postgres и на больших объемах ведут к Seq Scan или дорогим Bitmap Scan.
* **К проработке:**
  Устранить расхождение схемы и архитектурного принципа: нормализовать графовые связи в классические таблицы соединений (junction tables): `fact_lineage(fact_id, message_id)`, `fact_generalization(parent_id, child_id)`, `construct_evidence(instance_id, fact_id)`.

### 2.6. Конструкты Келли: психологический фетиш vs прикладная польза для LLM
* **Где зафиксировано:** Р4, Р5, `06 §5`, `09`.
* **Суть проблемы:**
  Идиографическое ядро осей Келли позиционируется как главное теоретическое отличие Gestalt.
* **Где сломается:**
  1. **Мнимый детерминизм координаты:** В `09 §4` утверждается, что положение на оси вычисляется детерминированно из evidence. Но полярность и релевантность факта конкретной оси определяет LLM при экстракции. Детерминизм формулы поверх недетерминированных эвристик модели — иллюзия.
  2. **Непригодность для агента:** Агент получает в промпт строку: `стабильность ↔ новизна: 0.7 [в tooling] (conf: 0.85)`. Современные LLM плохо трансформируют абстрактные скалярные психологические координаты в конкретные правила генерации кода. Им требуются директивы (*«не предлагай экспериментальные библиотеки»*). Но директивы (прескриптивы) исключены из портрета решением Р9.
* **К проработке:**
  Проверить на раннем прототипе, насколько наличие сырых осей Келли в системном промпте реально меняет поведение LLM-агента без трансляции в поведенческие инструкции.

### 2.7. Однонаправленный лифт и ловушка загрязнения скоупа
* **Где зафиксировано:** `10 §3.4`, нить Н13.
* **Суть проблемы:**
  Правило «Лифт однонаправленный (`SESSION → PROJECT → USER`), понижений scope нет — только смерть».
* **Где сломается:**
  1. **Необратимая глобализация ошибки:** Если факт уровня проекта ошибочно извлечен как `USER` (например, в безпроектной сессии по правилу `10 §3.2`), он загрязняет контекст всех остальных проектов пользователя навсегда. Автоматического отката скоупа нет.
  2. **Ловушка однократных фактов (Н13):** Важнейшие персональные данные (*«я дальтоник»*, *«работаю в часовом поясе UTC+4»*), озвученные один раз в проектной сессии, получают `scope = PROJECT`. Из-за отсутствия повторов в других сессиях они никогда не получат ко-подтверждения и навсегда застрянут внутри одного проекта.
* **К проработке:**
  Ввести эвристику немедленного подъема для явных фактов о личности (`subject = user`), либо механизм ревизии и деградации скоупа при консолидации.

### 2.8. Метрика качества: замкнутый круг LLM-as-a-Judge
* **Где зафиксировано:** Р12, Р14, `11`.
* **Суть проблемы:**
  Качество оценивается через парный A/B-тест на golden-наборе, где арбитром выступает LLM-судья.
* **Где сломается:**
  LLM извлекает факты $\to$ LLM строит оси $\to$ LLM склеивает словари $\to$ LLM генерирует ответ $\to$ **LLM оценивает результат**.
  Возникает эхо-пузырь: модель-судья склонна поощрять многословие и формальную вежливость, воспроизводящую термины из промпта. Отсутствие объективных метрик выполнения задач (task completion, compilation success, rejection rate) превращает CI-регресс в замер внутренней согласованности галлюцинаций.
* **К проработке:**
  Дополнить golden-набор жесткими критериями: тесты на фактическую точность (отсутствие противоречий с базой), компиляция сгенерированного кода, процент правок кода разработчиком.

## 3. Чеклист первоочередных архитектурных решений для следующей сессии

1. [ ] **Read-path:** Определить механизм формирования поискового запроса (Query Rewriting vs гибридный префетч) перед обращением к HNSW/FTS.
2. [ ] **Дедупликация:** Спроектировать поведение Fast-Path при несовпадении свободных предикатов (как избежать появления противоречащих ACTIVE-фактов до запуска Reconciliation).
3. [ ] **Схема БД:** Нормализовать массивы `lineage` и `generalized_from` в таблицы соединений для обеспечения целостности FK и эффективных рекурсивных CTE.
4. [ ] **Параллелизм:** Спроектировать блокировки и транзакционные границы для сценариев одновременного чтения, обновления счетчиков и фонового supersession.
5. [ ] **Динамика времени:** Добавить влияние физического (календарного) времени на старение фактов внешнего мира (домен WORLD).
6. [ ] **Минимальный прототип ядра (Spike):** Заморозить расширение концепции и реализовать сквозной вертикальный срез (Ingest $\to$ Pure PG $\to$ Snapshot) на Java 21 для верификации базовых гипотез.
