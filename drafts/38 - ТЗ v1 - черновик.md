## 1. Область действия и глоссарий

### 1.1. Назначение

Gestalt — инфраструктурный middleware долгосрочной памяти для AI-агентов разработчика (B2D, Р26): идиографическая модель профессионального почерка инженера + семантическая WORLD-память проекта. v1 — квадрант AU (агент наблюдает человека, Р3), состав по Р12: **ядро + Construct-minimal + метрика + прескриптивы**. Не психодиагностика, не bossware, не HR-аналитика.

Тезис-чек (E6–E8) завершён: вердикт insufficient при положительном знаке (research/26 §7) — go на разработку; статистическое доказательство пользы — релизный гейт полного яруса (§8.4).

### 1.2. Вне области v1

Big-Five-проекции, workspace/мультиаренда (Р11), AA/UA/UU-квадранты (Р3), GraphStore SPI (Р7/Н15), LLM-микс read-path и агентный цикл (Р47, v2+), hosted API (Р11), полные Пиаже-циклы, repertory-grid (Р12), точная единица интерференции (Р27, v2).

### 1.3. Глоссарий

Не дублируется: канонический словарь — `docs/concept/06` §8 (термины с дисциплинарными источниками); таксономия процессов — 13. ТЗ ссылается, не чеканит терминов (Р22).

Ключевые для чтения ниже: Fact (STATE/NARRATIVE/EVENT, домен WORLD/PSYCHE, scope SESSION/PROJECT/USER — Р13), ConstructAxis/ConstructInstance (Р5), PortraitSnapshot (Р19), Encoding/Dreaming/Gestalting/Reconciliation (Р18), Dual-Path Tiered Assembly, standing context (Р47), прескриптив (Р12), Δопыт/w/w_floor (Р27), needle-rank (research/37 §6).

## 2. Доменная модель

Канон: `docs/concept/16` (Fact и WORLD), `09` (Construct), `14` (PortraitSnapshot), `10` (проекты/радиусы), `17` (динамика). Сводка сущностей:

| Сущность | Суть | Канон |
|---|---|---|
| Fact | тройка SPO + kind (STATE/NARRATIVE/EVENT) + домен (WORLD/PSYCHE) + scope + identity-набор (Р23); lineage, valid_time, supersession-связи | 16 §2 |
| ConstructAxis / ConstructInstance | биполярная ось (переиспользуемая, иерархия — v2) / положение observed с evidence lineage ≥2 | 09 §3–4 |
| PortraitSnapshot | материализованная проекция: CRITICAL → CONSTRUCTS (директивы) → PREFERENCES; детерминированная, 0 LLM | 14 |
| Portrait | пара (user_id, project_id) + безпроектный NULL-дефолт (Р32) | 14 §2 |
| Прескриптив | рекомендация; отдельное хранилище (Р9), минимальная форма — канал фидбека | Р12 |
| Словарь (оси/предикаты/subject-имена/conditions-теги) | проекция над facts, не хранимая сущность; консолидация — dictionary_pairs | Р25 |

## 3. Функциональные требования (EARS)

Модули: ING (ингест-адаптеры), ENC (Encoding + дедуп), DRM (Dreaming), GST (Gestalting), RCL (Reconciliation), SNP (PortraitSnapshot), RDP (read-path), COR (Correction), MET (метрика/eval), INF (инфраструктура).

### 3.1. Ингест (ING)

- **REQ-ING-001** [Р47]. Когда хост-система отправляет событие сессии (минимум `UserPromptSubmit` и `AssistantResponse`; полный набор — SessionStart/PostToolUse/SessionEnd), система должна принять его через thin-shim адаптер без собственной семантической обработки.
- **REQ-ING-002** [Р47]. Когда адаптер получает реплику с вложенным `tool_result`, система должна отфильтровать его до инжеста (07 §5 п.7).
- **REQ-ING-003** [Р47]. Когда пользователь запускает деплой, система должна поставляться как библиотека (embed) + sidecar; hosted API — вне v1.

### 3.2. Encoding и дедуп (ENC)

- **REQ-ENC-001** [Р8]. Когда сообщение принято в инжест, система должна обработать его LLM-вызовом максимум один раз (Pass-Once: батч-экстракция, накопление 15–20 реплик / 1500–2000 токенов, age-flush — research/25).
- **REQ-ENC-002** [Р23]. Когда батч экстракции вернул STATE-факт, система должна выполнить двухшаговый детерминированный дедуп: identity-lookup `(owner, scope, project_id, subject_norm, predicate_norm, conditions)` → равенство нормализованного object = reinforcement (+1, дубликат не создаётся); отличие = кандидат supersession; новый identity = новый факт.
- **REQ-ENC-003** [Р23]. Когда два факта одного identity получают разные object, система должна обеспечить инвариант ≤1 ACTIVE на identity (частичный unique-индекс).
- **REQ-ENC-004** [Р25]. Когда экстрактор формирует промпт, система должна включить в него словарь домена (top-150 по использованию + 50 «яслей» неподтверждённых; naming-политика, regex-валидатор).
- **REQ-ENC-005** [Р25]. Когда object подпадает под канонизатор (url → путь → версия → количество → строка), система должна нормализовать его детерминированно; сомнительная близость — кандидатом судье словарей, не тихой склейкой (принцип консервативности).
- **REQ-ENC-006** [Р25]. Когда появился сигнал кандидата склейки (pg_trgm ≥ порога / fingerprint ко-использования / косинус ≥ 0.85), система должна поставить пару в очередь judge-батча Reconciliation (не склеивать на fast path).
- **REQ-ENC-007** [Р38]. Когда факт записан, система должна вычислить surprisal = 1 − max_sim к ближайшему ACTIVE-факту (переиспользование эмбеддинга семантической ветви, 0 LLM) как приоритет разбора Dreaming.
- **REQ-ENC-008** [Р23]. Когда conditions различаются при равном (subject, predicate), система должна создать sibling-факт (сосуществующие истины), не supersession.
- **REQ-ENC-009** [research/37 R2]. Когда факт предназначен для recall, система должна обеспечить наличие statement (естественно-язычная строка); SPO-склейка без statement в селекции не участвует (неселектируема: kindId, ранг 4312 — E8).
- **REQ-ENC-010** [research/37 R2]. Когда знание устанавливается, система должна фиксировать его самостоятельным фактом (гранулярность: «дев-стенд = IP» — фактом о стенде, не строкой конфига).

### 3.3. Dreaming (DRM)

- **REQ-DRM-001** [Р39]. Когда наступила каденция ИЛИ порог очереди разбора, система должна запустить прогон Dreaming в drain-режиме (очередь write-time кандидатов: supersession, лифт scope, свёртка, пост-мортем; full-scan запрещён).
- **REQ-DRM-002** [Р39]. Когда прогон Dreaming обрабатывает кандидатов, все вердикты должны быть детерминированными (триаж 10 §2, счёт Р31, кластеризация 0 LLM); LLM — только синтез statement свёрток, ≤2 батча/прогон (мини-конкорданс, консервативность, идемпотентность).
- **REQ-DRM-003** [Р29/Р39]. Когда свёртка создана, её атомы должны перейти в RETIRED (absorbed; generalized_from; горячий набор — только ACTIVE, инвариант 16 §3.1).
- **REQ-DRM-004** [Р39]. Когда сессия закрыта, пост-мортем должен инвентаризировать SESSION-факты (лифт с реактивацией Р28 / soft-гашение) + supersession-кандидаты + свёртка-проверку.
- **REQ-DRM-005** [Р33]. Dreaming не должен создавать конструкты и не должен трогать PSYCHE-статусы (слои Р33).
- **REQ-DRM-006** [Р28]. Когда Dreaming выполняет лифт scope или кросс-проектное ко-подтверждение, last_seen фактов должен двигаться (реактивация).

### 3.4. Gestalting (GST)

- **REQ-GST-001** [Р33]. Когда наступила каденция (сутки) ИЛИ накоплено N новых фактов PSYCHE, система должна запустить Gestalting.
- **REQ-GST-002** [Р5/Р33]. Gestalting должен выполнять: emerging-индукцию из пула Fact/PSYCHE (не из логов — Р8), LLM-naming осей, переводы статусов emerging→active→drifted (гистерезис K=2, Р27/Р31).
- **REQ-GST-003** [Р33]. Когда обнаружена кросс-проектная поведенческая черта, Gestalting должен провести PSYCHE-индукцию (WORLD-компетенции — контур Dreaming, разводка Р33).
- **REQ-GST-004** [Р5]. Когда позиция инстанса вычисляется, система должна считать её детерминированно из evidence (LLM — только именование оси).
- **REQ-GST-005** [Р31]. Когда две оси дают сигнал merge (trgm полюсов + Жаккар lineage + косинус пары «poleA ↔ poleB»), система должна провести каскад Р25 (кластеризация 0 LLM → judge с конкордансом инстансов → merge-миграция: union lineage, тай-брейк имени).

### 3.5. Reconciliation (RCL)

- **REQ-RCL-001** [Р10]. Фоновая Reconciliation должна обеспечивать self-healing: lease + backoff + poison-изоляция для всех джоб.
- **REQ-RCL-002** [Р19]. Когда наступил период пересборки (дефолт 10 мин, конфиг), система должна пересобрать dirty-слепки детерминированно (0 LLM).
- **REQ-RCL-003** [Р43]. Когда получен сигнал форс-пересборки (COR), система должна выполнить single-flight пересборку соответствующего слепка немедленно.
- **REQ-RCL-004** [Р25]. Judge-батч консолидации словарей должен работать в границах лимитов время/объём, drain-режим, идемпотентность через dictionary_pairs (UNIQUE namespace, a, b).
- **REQ-RCL-005** [Р46]. Reconciliation должен исполнять детерминированные проверки целостности графа памяти (циклы supersession, orphan-lineage и др.) без LLM.
- **REQ-RCL-006** [Р47]. Когда EmbeddingProvider недоступен, система должна деградировать fail-open (write-path — очередь до-эмбеддинга; read-path — FTS-only), не отказом сервиса.

### 3.6. PortraitSnapshot (SNP)

- **REQ-SNP-001** [Р19]. Слепок должен собираться из секций CRITICAL → CONSTRUCTS (директивы) → PREFERENCES, бюджет ≤40×200 символов на секцию-строку, `(unconfirmed)` при conf < 0.8.
- **REQ-SNP-002** [Р32]. Гранула слепка — пара (user_id, project_id) + безпроектный NULL-дефолт; глобальные секции дублируются между слепками.
- **REQ-SNP-003** [Р19]. Инвалидация — cutoff: `max(system_time входов) > cutoff`; события write-path слепок не трогают; dirty-flag отвергнут.
- **REQ-SNP-004** [Р40]. PREFERENCES — предикат селекции при пересборке: стабилизированные Fact/PSYCHE с count(DISTINCT session_id по lineage) ≥ K (дефолт 2), не событие.
- **REQ-SNP-005** [Р19]. Чтение слепка должно выполняться за O(1) от размера памяти (готовый профиль; SLA — §7).
- **REQ-SNP-006** [Р28]. Когда факт доставлен в контекст сессии (селекция в слепок / recall с доставкой в Top-K), система должна двинуть его last_seen (использование = подкрепление); голый retrieval-hit без доставки — не двигает.

### 3.7. Read-path (RDP) — Dual-Path Tiered Assembly

- **REQ-RDP-001** [Р47]. Read-path v1 должен состоять из двух независимых каналов: standing context (слепок) + dynamic WORLD-recall (Top-K по запросу `recall(query, [filters])`, 29 §3).
- **REQ-RDP-002** [Р47]. Dynamic recall должен быть multi-signal: dense (pgvector) + BM25 + entity-boost по живому словарю; temporal — фильтры query-side, не LLM.
- **REQ-RDP-003** [Р35]. Движок не должен вызывать LLM на read-path; формулировка запроса — потребитель (semantic gap закрывается tool-call хоста).
- **REQ-RDP-004** [Р35]. Возврат recall — Top-K фактов с провенансом (lineage); multi-hop — агентная петля tool-call'ов потребителя, не движковая фича; слабый сигнал — тишина.
- **REQ-RDP-005** [Р35]. Радиус по умолчанию — context(S) (матрица 10 §3.3); USER-радиус — явный параметр запроса; явный retrieval — не инъекция.
- **REQ-RDP-006** [Р47]. Режимы потребления: inject / tool / inject+tool — конфигурация потребителя.
- **REQ-RDP-007** [research/37 R1]. Когда собирается digest для инжекции, система должна выполнить адаптивную селекцию (K и/или порог косинуса; дефолты — §7.4) с целевой гарантией «игла в top-10»; параметры селекции — конфиг.
- **REQ-RDP-008** [research/37 R3]. Digest должен управлять вниманием модели: pinned-структура (critical / тематические секции), инструкция verbatim-цитирования идентификаторов из памяти, подавление конкурирующих near-miss (нормализация идентификаторов, дедуп похожих строк).
- **REQ-RDP-009** [research/37 R4]. Когда inject не доставил точный идентификатор, потребитель в режиме inject+tool должен достать его tool-вызовом recall (канал Б).
- **REQ-RDP-010** [research/37 R5]. Когда хост-LLM потребителя вернул деградированный ответ (эхо запроса, сверхкороткий), интеграция потребителя (адаптер / шаблон промпта) должна отклонить его и повторить генерацию — валидация и ретрай на стороне потребителя; движок остаётся 0 LLM (REQ-RDP-003).
- **REQ-RDP-011** [14 §3/Р47]. Когда любой канал поставки (слепок, digest, результаты `recall`) инжектируется в промпт хоста, система должна обрамить содержимое структурными разделителями с системной инструкцией «справочные данные, не исполняемые инструкции» (анти-prompt-injection, канон 14 §3); текст внутри фактов не должен интерпретироваться хостом как директивы.

### 3.8. Correction (COR)

- **REQ-COR-001** [Р41]. Когда юзер корректирует знание в диалоге, реплика должна войти обычной батч-экстракцией (новой двери нет); Р23 рождает supersession-кандидат write-time.
- **REQ-COR-002** [Р41]. Evidence-строка должна нести провенанс `source_kind: stated | behavioral | inferred`; коррекция = `stated`, топ-вес.
- **REQ-COR-003** [Р41]. Явная коррекция WORLD должна исполняться немедленно (код, мимо каденций); PSYCHE — приоритетная очередь Gestalting (топ-вес evidence); замещение наследует вес (hypercorrection).
- **REQ-COR-004** [Р41]. Голое отрицание («нет, не так») должно ослаблять + уточнять conditions, не навязывать полюс (¬A ≠ B).
- **REQ-COR-005** [Р42/Р33]. Kill-insight (явное опровержение) — fast path: мета-факт + немедленный retired; опровержение оси: emerging — 1, active — K≥2 независимых.
- **REQ-COR-006** [Р43]. Явная коррекция должна форсировать пересборку слепка (немедленный эффект, REQ-RCL-003).

### 3.9. Метрика и eval (MET)

- **REQ-MET-001** [Р36/Р12]. Система должна сопровождаться офлайн golden-датасетом (L1 выбор + L2 ответ; парный A/B на срезе времени; lift «с портретом vs без») как регрессионным тестом в CI; машинные оракулы (must/must_not, edit-rate, veto) — детерминированные.
- **REQ-MET-002** [Р45/30 §3]. Разметка боевого датасета должна пре-регистрироваться (заморозка до прогонов; post-hoc правки запрещены); diagnostic probes — отдельным потоком, не в golden.
- **REQ-MET-003** [30 §3]. Порядок прогона: replay → wcheck → чистка точек → arms; must-токен = ядро ответа (R6).
- **REQ-MET-004** [research/37 R1]. Needle-rank (ранг must-факта после селекции) должен быть стандартной метрикой регресса в CI (детерминированный, дешёвый).
- **REQ-MET-005** [Р14]. Golden-датасет обязан содержать: C-точки (no-false-memory, leak = fail), temporal- и multi-hop-точки; filler-инвариант (полезные факты выталкиваются за окно контроля).
- **REQ-MET-006** [Р37]. Адаптер read-path под внешние бенчмарки (LongMemEval, BEAM) — health-отчёты, не CI-гейт.
- **REQ-MET-007** [Р36/Р45]. Релизный гейт v1 — полный ярус: 100–300 точек, LLM-судьи, McNemar; go-условие — положительный lift на решённых парах (мощность — ADR 28 §3.5).
- **REQ-MET-008** [Р12]. Онлайн-контур L3 = acceptance-rate прескриптивов (kill-insight + acceptance), минимальная форма без UI-советчика.

### 3.10. Инфраструктура (INF)

- **REQ-INF-001** [Р7]. Хранилище — Pure PostgreSQL 16+ с pgvector; графовые workload'ы — таблицы рёбер + recursive CTE + JSONB/GIN; GraphStore SPI — v2+.
- **REQ-INF-002** [Р11]. Изоляция юзеров — RLS по user_id; workspace исключён; API v1 не закладывает workspace в пути.
- **REQ-INF-003** [Р17]. Ядро — Java 21 LTS, zero-dependency/zero-framework (чистые SPI, виртуальные потоки); фреймворк-адаптеры — внешние модули.
- **REQ-INF-004** [Р47]. `EmbeddingProvider` SPI: Remote-API (дефолт) + In-JVM ONNX (enterprise/air-gapped); пиннинг модели на базу (`gestalt_meta`; несовпадение = отказ старта; смена модели = миграция + перекалибровка порогов).
- **REQ-INF-005** [Р29]. Исторические WORLD-факты (SUPERSEDED/RETIRED) — вне горячего набора; доступ: полный GIN(anchor), навигация superseded_by/generalized_from, temporal query-side.
- **REQ-INF-006** [Р46]. Схема БД накатывается миграциями; каркас eval уже использует ту же схему фактов (переиспользование опыта спайка/eval — донор кода).
- **REQ-INF-007** [Р10]. Конфигурация — иерархический конфиг со снапшотом состояния; недетерминированные лимиты итераций запрещены.
- **REQ-INF-008** [Р17]. Лицензия — Apache 2.0.
- **REQ-INF-009** [Р17/Р33]. Когда выполняется любая из четырёх LLM-точек (экстракция, синтез свёрток, naming осей, judge словарей), система должна фиксировать структурированную запись телеметрии (контур, точка, латентность, токены, статус) через абстракцию логирования ядра (`System.Logger` / `slf4j-api`, без привязки к реализации — 29 §1.1); пятая LLM-точка — нарушение инварианта Р33, не вводится.
- **REQ-INF-010** [Р17/29 §1.1]. `gestalt-server` должен экспонировать healthchecks (liveness/readiness, включая доступность БД и провайдеров эмбеддингов/LLM) и метрики Micrometer (глубины очередей Reconciliation, lease/poison-счётчики, латентности LLM-точек, бюджеты блоков поставки 14 §6).
- **REQ-INF-011** [Р47/Р11]. `gestalt-server` должен выставлять поверхность REST + MCP для не-JVM хостов (деплой sidecar): ингест-хуки (§3.1), чтение слепка, `recall()`, админ-джоб; пути API не содержат workspace (Р11); приём ингеста идемпотентен по `(session_id, message_id)`.
- **REQ-INF-012** [Р11]. Все доменные таблицы должны быть защищены RLS-политиками по `owner_id` (контекст сессии БД `app.user_id`); изоляция подтверждается тестом (чужой `owner_id` не читается и не пишется).
- **REQ-INF-013** [Р7/29 §5]. Партиционирование в v1 не вводится (объёмы v1 — до миллионов фактов, Pure PG справляется, Р7); на `facts` задаётся BRIN по `system_time` для сканов истории; пересмотр решения — по метрикам observability (рост объёма/латентности), не заранее.

## 6. Java API/SPI (порты ядра)

- `EmbeddingProvider` — контракт по 29 §2 (метаданные/batch/single; single < 50 мс бюджет; пиннинг; fail-open).
- `LlmProvider` — контракт LLM-вызовов ядра: четыре вызововых метода = четыре LLM-точки (Р33/Р39) + `modelInfo()` — метаданные модели без LLM-вызова (пиннинг → `gestalt_meta`); закрытие позиции 29 §5:

```java
public interface LlmProvider {
    LlmModelInfo modelInfo();                        // id модели → gestalt_meta
    ExtractionOut extract(ExtractionIn batch);       // Encoding: батч реплик → факты (структурированный вывод)
    AxisNamingOut nameAxis(AxisNamingIn candidates); // Gestalting: кандидаты полюсов → имя оси
    DictionaryVerdict judge(DictionaryPairIn pair);  // Reconciliation: пара словаря + конкорданс → вердикт
    StatementOut synthesize(SynthesisIn atoms);      // Dreaming: атомы → statement свёртки
}
```

  Свойства контракта: `judge` — детерминированный режим (temperature 0; урок детерминизма судьи — спека 28 §5); бюджеты/таймауты — по типу задачи (конфиг); устойчивость — декоратор ядра над провайдером (экспоненциальный backoff + jitter, 29 §1.1), провайдер — только транспорт; отказ провайдера: write-path удерживает батч в очереди (Pass-Once — сырьё не теряется и не расформировывается), read-path не затронут (0 LLM, Р35); новая LLM-точка = расширение SPI + нарушение инварианта Р33 — в v1 запрещено.
- `recall(query, [filters])` → Top-K + провенанс (Р35, 14 §6).
- Snapshot read API (O(1) чтение готового профиля, Р19).
- Ingest-хуки адаптера (Р47: SessionStart/UserPromptSubmit/AssistantResponse/PostToolUse/SessionEnd).

### Границы модулей (29 §1.1)

```
gestalt-spring-boot-starter ──────┐  (автоконфигурация: контекстный DataSource, application.yml → конфиг ядра)
                                  ▼
gestalt-core (zero-framework) ◄── gestalt-reconciler (демон фоновых джоб: DRM/GST/RCL каденции)
   ▲  порты: javax.sql.DataSource · System.Logger/slf4j-api · java.net.http · EmbeddingProvider · LlmProvider
   │
gestalt-server (REST/MCP + HikariCP + Micrometer + маскировка логов; sidecar = server + reconciler; SchemaMigrator при старте)
```

Правила изоляции: `core` не зависит ни от одного модуля и ни от одного фреймворка (Р17); `reconciler` и `server` зависят только от `core`; `starter` собирает `core` в JVM-хост; единственная точка входа хоста — API `core` (thin-shim адаптеры поверх, Р47); миграции схемы — программный API `core` (`SchemaMigrator`, донор — eval-каркас, REQ-INF-006; уточнение 29 §1.1: единый мигратор вместо Flyway-in-server — работает в обоих деплоях embed/sidecar), `server`/`starter` исполняют его при старте.

Сигнатуры — Java interface, без реализации (правило 30 §1).

## 7. NFR и числовые дефолты

### 7.1. Производительность (калибровка v0 — research/25; продуктовые пороги — приёмка)

- Слепок: O(1) от размера памяти; локально p95 0.47 мс — продуктовый SLA определить на стенде первой интеграции (§7.4).
- Encoding: Pass-Once — 4 вызова LLM на 61 реплику (−93,4% к по-репличному), ~174 токена/реплика; экстракция ≤ 2 LLM-точек на батч.
- Read-path: слепок O(1); recall — десятки мс (multi-signal SQL); движок — 0 LLM.
- Dreaming/Gestalting — фоновые каденции, вне критического пути.

### 7.2. Достоверность/целостность

- Дедуп 46,7% (v0-калибровка спайка) без потери событий (смена object = событие).
- Инварианты Р23/Р46 + проверки целостности графа в Reconciliation.
- No-false-memory: C-leak = 0 на golden (E8 подтверждает).

### 7.3. Надёжность

- Reconciliation self-healing (lease+backoff+poison); fail-open эмбеддингов (Р47); fail-fast при неконсистентности модели эмбеддингов с базой.

### 7.4. Числовые дефолты v1 (сводный перенос, Н8)

## 8. Стратегия тестирования

### 8.1. Пирамида (Р36)

Тысячи детерминированных unit-тестов ядра (следствие Pass-Once) → центовые компонентные LLM-тесты → golden-датасет (вершина, фаналка) → внешний трек бенчмарков (health, не гейт).

### 8.2. Переносы эмпирики eval (полный чек-лист — спека 30 §3)

Пре-регистрация разметки; frozen golden ≠ diagnostic probes; адаптивная селекция + needle-rank в CI; процесс replay → wcheck → чистка → arms; must = ядро ответа; метрика = регресс CI (машинный ярус) + судейский ярус релизно.

### 8.3. Каркас

Используется каркас `eval/` (Р45, спека 28): replay-чекпоинты, fingerprints, PG-источник истины; golden-датасет v1 собирается из живых логов по протоколу 28 §6 (пре-регистрация обязательна).

### 8.4. Релизный гейт (полный ярус)

100–300 точек, судьи, McNemar exact, α = 0.05; go — положительный lift на решённых парах; критерии условного no-go — по рамке 28 §4.2 (мощность: ~20 решённых пар при перевесе 2:1). Insufficient-вердикт E8 закрывает добором точек, не пересмотром концепции.
