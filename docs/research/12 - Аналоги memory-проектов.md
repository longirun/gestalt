## 12.1 NGT Memory (ngt-memory/ngt-memory)

**Паспорт.** https://github.com/ngt-memory/ngt-memory · Python/FastAPI + torch · v0.23–0.24 · соло-проект (9 коммитов; судя по номерам экспериментов в README — до Exp 44 — разрабатывался вне GitHub) · лицензия **BSL 1.1** (коммерческое использование платно, Apache 2.0 только с 2030) · hosted API ngt-memory.ru.

**Класс системы — иной, чем Gestalt.** NGT — «memory-прокси» для чат-приложений: `POST /chat` сам вызывает LLM и инжектит память в системный промпт; `session_id` — единица изоляции; состояние в памяти процесса (Redis — опция, single-worker). Мы — факт-центричный memory-server: PG-ядро (Р7), lineage, RLS (Р11), MCP-интерфейс. NGT для нас не шаблон, а полигон: дешёвые полевые испытания паттернов.

Ядро: 4-уровневая иерархия на torch (Sensory FIFO → Working с importance-гейтом → Episodic → Semantic-центроиды), promotion по важности, «Dream Phase» (агрессивная консолидация с низкими порогами), level-dependent decay, хеббовский граф ассоциаций концептов. UserProfile — 7 захардкоженных regex-слотов (name/age/city/diet/allergies/work/family_status) с confidence, историей изменений и «окном коррекции».

### Что берём

1. **Методика оценки — лучшее в проекте → Р14.** Их eval-контур (`eval/deep_eval.py`, 7 осей, 17 типизированных сценариев, сырые данные коммитятся):
   - контрольная ось **no-false-memory**: вопросы не по теме, leak-rate на уровне ответа LLM (их результат: precision 1.00 — память молчит про Rust/Postgres в вопросе про банановый хлеб). У нас в 11 мерялось «вспоминает», но не «не выдумывает» — дыра закрыта;
   - **filler-ходы**: факты выталкиваются за окно истории нейтральной болтовнёй, baseline физически не знает ответа → чистый lift (их бенч: 0/8 vs 8/8);
   - **contradiction-сценарии**: память должна исправить пользователя («вы трезвый пять лет — вино не подходит»); поведенческий тест сильнее recall, бьётся в мишень 11 §2 (наблюдаемое поведение);
   - **cost-ось**: латентность и входные токены «с памятью vs без» — подтверждение включения стоимости в рамку 11;
   - культура честной отчётности: провалы публикуются (distractor 0.50/0.50 в обоих режимах), оговорки о грубости keyword-скоринга.
2. **Формат golden-датасета** — типизированный jsonl-сценарий (факты + filler + вопрос + `expect_keywords` + категория) → стартовый формат нашего набора (11 §3, Р14-в).
3. **Полевое подтверждение П2/Н3 (PortraitSnapshot → Р19).** `UserProfile.as_prompt_block()` — буквально мини-слепок: структурированный дайджест в системный промпт с маркерами `(unconfirmed)` при confidence < 0.8 и пометкой «highest priority». Два штриха к Р19: маркеры уверенности в слепке; приоритетная позиция критичных PSYCHE-фактов над WORLD-recall (их distractor-промах: retrieval поднял «board games» вместо факта об инвалидности — иллюстрация, зачем нужен слой профиля, а не только поиск).

### Кандидаты на обсуждение → Н10

- **novelty-as-importance**: важность = 1 − max_sim к ближайшему прототипу, детерминированно, на write-time — дешёвый surprisal-сигнал приоритизации fast path (перекликается с Р10 «surprisal-подсказки без LLM»).
- **usage-based reinforcement**: retrieval-hit продлевает жизнь факта (противостоит decay). Напряжение с инвариантом Р10 «подтверждение ≠ использование».

### Что не берём

- **Regex-слоты профиля** (7 слотов, RU/EN-паттерны, падежи не нормализуются) — номотетический тупик; живая иллюстрация к Р4/Р5: слот-схема не масштабируется на идиографического человека.
- **Центроиды-прототипы** («семантика» = running mean векторов) — теряют текст факта и lineage; наш slow path (Р6, сон с lineage) строго богаче.
- **Torch-ядро / «нейропластичность»** — continual-learning-механика (replay с шумом, GNN-стайл), к памяти LLM отношения почти не имеет; тянет torch в прод-слой без пользы.
- **Хеббовский граф ассоциаций** — их собственный eval: graph_on ≡ graph_off по всем retrieval-метрикам (recall@5/MRR/hit@1). Независимое подтверждение Р7.
- **Session-as-tenant + in-memory store** — подтверждение Р11 (RLS, PG, иерархия сущностей).
- **Роль чат-прокси** — калибровка для Н5: память упакована в `/chat`-шлюз; наш выбор — memory-API (MCP), не прокси.

### Лицензия

BSL 1.1: чтение и заимствование идей — да, копирование кода — нет. Режим тот же, что с Honcho.

## 12.2 Honcho (Plastic Labs)

**Паспорт.** https://github.com/plasticlabs/honcho · Python/FastAPI + SQLAlchemy async + Postgres/pgvector (+ Turbopuffer/LanceDB опции), Redis (кэш сущностей), DB-as-queue без внешнего брокера · v3.0 (по открытой документации и спецификациям, сентябрь 2026) · лицензия **AGPL v3** · hosted-продукт Plastic Labs. Два процесса: API-сервер (enqueue + Dialectic inline на запрос) и deriver-воркер (Deriver / Summarizer / Dreamer + in-process Reconciler).

**Класс системы.** Memory-API для мульти-агентных чатов: персистентные наблюдения за peers (collections per observer→observed), query-интерфейс Dialectic (агентный tool-loop с бюджетной лестницей). Ближайший к нам по классу аналог.

**Историческая роль — снята (Р15).** Gestalt стартовал как переработка Honcho (Р1), но статус понижен до обычного аналога: ни архитектурной оглядки, ни data-compat обязательств. Перенос данных, если когда-нибудь понадобится, — обычный адаптер «из их памяти в нашу», как из любого другого проекта. Раздел консолидирует архитектурные выводы и сопоставление подходов в рамках общего реестра аналогов (Р15, Р16).

### Что берём (поглощено реестром)

1. **Гибридная дисциплина fast/slow → Р6.** Fast path: батч-экстракция ~0.2–0.3 LLM-вызова на сообщение (накопление work-unit ≥512 ток. → окно ≤1024 ток., age-flush 1800 с) + детерминированный дедуп без LLM-суждений. Slow path «сон»: порог ≥50 новых explicit-фактов на коллекцию, ≥8 ч между снами, отложен на 60 мин простоя, активность юзера отменяет; порог считает только explicit — анти-feedback. Попутно: легенда «Honcho делает ~10 проходов по сообщениям» опровергнута (single-pass deriver, мульти-стадийность — это v2-эра и tool-лупы Dreamer'а по хранимым фактам).
2. **Reconciler-паттерн → Р10.** Self-healing PG↔vector конвергенция (sync_state + lease по last_sync_at + attempts + backoff + poison `failed`), отложенный эмбеддинг, быстрый путь embed_now с гейтом in-flight, не тратящий retry-бюджет, GC soft-delete (векторы → потом строки). Для pure-PG — must.
3. **Усиление вместо дублирования → Р10.** `times_derived`: повторный вывод дубликата = атомарный инкремент; «most derived» — first-class ранжирование. Повторы — сигнал, не шум.
4. **Провенанс в JSONB + GIN containment** (дерево premises/children в `source_ids`) вместо графовой БД — независимая валидация Р7.
5. **Write-time fan-out наблюдателей → Р10, 07.** Один LLM-вызов → записи во все коллекции наблюдателей; мульти-наблюдение множит записи/эмбеддинги, не LLM-цены.
6. **Session-purity explicit-фактов** (dedup не пересекает сессии для explicit; derived — кросс-сессионный) и **fail-closed на пустых IN** (`1=0` / `Eq AND NotEq`) → Р10.
7. **Иерархический конфиг message > session > workspace > global** со снапшотом разрешённого конфига в payload задачи (батчи реплеебельны) → Р10.
8. **Surprisal-подсказки без LLM** (KD-дерево на эмбеддингах, выбор аномалий) → Р10; перекликается с кандидатом Н10-а из NGT.

### Кандидаты (в нитях)

- **Peer cards** — лёгкий портрет в `internal_metadata` (префиксы IDENTITY/ATTRIBUTE/RELATIONSHIP/INSTRUCTION, ≤40×200 симв., структурная валидация, перепись Dreamer'ом, инжект в промпт) → каркас для Р19 (PortraitSnapshot).
- **Бюджетная лестница reasoning-уровней Dialectic** (minimal=1 … max=10 вызовов, per-level модель+инструменты) → лестница бюджетов → Н5 (в v1 read-path без LLM — Р19); Р10 «рассмотреть».
- **Dialectic dual-path префетч**: два раздельных поиска (explicit отдельно от derived — против размывания релевантности) до агентного лупа → кандидат в read-path (Н5; `ContextProducer` — Р18).

### Что не берём

- **Баги** (Р10 «не наследовать»): векторы удалённых сообщений не чистятся никем; chunk-позиции на row-id ordering.
- **Workspace-изоляция** через namespacing в трёх слоях → у нас RLS по `user_id` (Р11).
- **Мульти-бэкенды векторных хранилищ** (Turbopuffer/LanceDB + миграционный dual-write `VECTOR_STORE_MIGRATED`) — v1 = pure PG (Р7).
- **Redis-кэш сущностей** (cashews) — лишний компонент при одной СУБД.
- **Двухпроцессная упаковка** API-воркер — вопрос упаковки Н5, не догма.
- **Rolling-саммари каждые 20/60 сообщений** — главный множитель per-message LLM-цены после экстракции; у нас эпизодика хранится как есть (Р8), сжатие — только в slow path с lineage.

### Данные и лицензия

AGPL v3: строгий копилефт на исходный код. Gestalt реализуется с нуля на Java 21 под лицензией Apache 2.0 (Р17); перенос данных, если возникнет потребность, — внешний адаптер открытого формата экспорта (Р15); golden-набор метрики из логов — использование данных, не совместимость (Р12).

## 12.3 HippoGraph Pro (artemMprokhorov)

**Паспорт.** https://github.com/artemMprokhorov/hippograph-pro · Python, Docker, SQLite (`memory.db`) · 229 коммитов, 25★, research-система (соло + AI-коллаборация) · single-user by design (~1000 заметок в проде, деградация после ~2000) · zero-LLM-cost: GLiNER + spaCy + sentence-transformers (bge-m3 эмбеддинги, bge-reranker-v2-m3 реранкер, всё локально) · лицензия — **MIT** (README заявляет dual/commercial, но файл LICENSE — чистый MIT).

**Класс системы.** Self-hosted графовая ассоциативная память личного AI-агента: MCP-интерфейс (19 tools, SSE), CLI, 2D/3D-визуализация графа. Четвёртый класс в реестре: NGT — чат-прокси, Honcho — мультиарендный memory-API, HippoGraph — single-user граф-память. Тезис «model = substrate, personality = memory»: идентичность агента пережила 10 модельных инстансов (4 Claude + 6 Gemini) без потери личности и отношений — полевое подтверждение нашей рамки (Р3: смена модели = смена эпохи при непрерывности памяти; PSYCHE-домен как субстрат идентичности).

### Что берём

1. **Двухтрековая дисциплина бенчмарка → Р12/Р14.** Benchmark-config ≠ production-config, явно разведены («прямое сравнение невалидно»), прогресс трекается внутри трека. Урок: конфигурации Golden-набора и прода версионируемо разводить, цифры разных треков не смешивать.
2. **Негативный результат SUPERSEDES → уточнение Р6.** Штраф на superseded-факты в retrieval вредит во всех комбинациях параметров (4 прогона); старые факты — не шум, а reasoning-контекст. Вывод: supersession меняет **статус** факта (историчность), но не подавляет retrieval. Рёбра оставлены как структурные признаки для будущего reasoning-слоя.
3. **Sensitivity-таблица компонентов — независимое подтверждение Р7.** Реальный вклад: cross-encoder reranker +9.1pp, стратегия чанкинга +21.7pp; spreading activation — **+0.1pp** (ничтожен), «биологические» рёбра на внешнем бенчмарке ≈ 0. Решают ранжирование и гранулярность, не граф-магия.
4. **PCB (Personal Continuity Benchmark) — подтверждение и антиурок для Р12/Р14.** Внутренний бенчмарк «помнит ли система *тебя*» на живых данных — ровно наша мишень (наблюдаемое поведение юзера, а не QA по чужим диалогам). Антиуроки: keyword-матчинг хрупок (расширение ключей двигало категории на ±100pp), n=26–35 вопросов мал, а «100%» случилось после фикса бага DB_PATH — до фикса измерение шло не против той БД. Итог: self-benchmark систематически врёт; внешний арбитр (парный A/B + judge) обязателен.
5. **Гранулярность сна light/deep** (лёгкий каждые 50 заметок: decay рёбер, PageRank, дедуп-скан; глубокий ежедневно: relation extraction, конфликты, снапшот+откат) + `sleep_compute(dry_run)` — превью консолидации без изменений → имплементационные заметки к Р6/Н6.
6. **H3-урок: якоря после консолидации, не при ingestion** — «граф должен устояться» перед навигационной индексацией; перекликается с нашим fast/slow (Р6): структурная индексация — прерогатива slow path.

### Кандидаты → Н10

- **Prospective memory**: намерения юзера (`add_intention` / `complete_intention`, PROSPECTIVE_BOOST поверх decay) — планы и обещания переживают забвение и всплывают в retrieval. Сущности «намерение» у нас нет: это факты с будущим valid_time или отдельный вид (v2+).

### Что не берём

- **Zero-LLM-cost как принцип.** Их же данные о цене: temporal-вопросы — «структурный потолок» retrieval-only (35–67%, нужны LLM-рассуждения), E2E QA F1 = 38.7% против GPT-4 32.1%. Наш Р8 — осознанная противоположность: LLM на семантических границах. GLiNER-NER ≠ семантическая экстракция фактов с lineage.
- **Emotional weighting как схема — данные да, схема нет.** Поля tone/intensity/reflection + EMOTIONAL_RESONANCE-рёбра (Jaccard по тон-тегам, нормализация RU→EN) — номотетический фикс аффекта, тот же тупик, что слоты NGT (Р4/Р5). Эмоция входит у нас как **данные**: «злился на X» — легитимный PSYCHE-факт/evidence; повторяющийся паттерн родит ось индукцией в slow path («спокойный ↔ вспыльчивый») — если эмоциональность для юзера диагностична, шкала появится сама, с lineage ≥2. У них же emotional_modulation — стабильно слабейший индикатор их consciousness-чека (0.23–0.33).
- **Anchor policies — костыль отсутствия факт-модели.** Реестр защищённых категорий (3 слоя: hardcoded baseline / юзер-политики через MCP / авто-обнаружение) нужен, потому что у них заметки с категориями — защищать можно только категории. Ядро потребности — явная перманентность («запомни навсегда: аллергия на пенициллин») — у нас выражается условием на факте: `permanence = user-asserted` → хвост Н4, без реестра политик и подсистемы.
- **Consciousness/emergence-метрики** (phi_proxy по IIT, индикаторы Butlin et al., composite 0.854 «STRONG») — нефальсифицируемы; показатели двигались манипуляцией выборки (self_ref 0.12→0.94 исключением якорей из cosine-поиска). Деннет-принцип (11 §1): измеримо только предсказание с внешним арбитром.
- **Spreading activation по всему графу на каждый запрос** — латентность 150мс–1с, деградация с плотностью рёбер (2.4M рёбер на 7k узлов ≈ 342/узел — граф раздут ассоциативными рёбрами; наш reinforcement-счётчик по Р10 рёбер не плодит). Подтверждение Р7: полный обход графа не окупается.
- **Биологические аналоги как архитектура** (амигдала/GABA/префронтальная кора для типов рёбер) — hardcoded магические веса (0.5×, 0.05, 0.20), grid-search-тюнинг, вклад ≈ 0 по их же sensitivity-таблице. Архитектурный парфюм.
- **SQLite single-user + config sprawl** (50+ env-переменных, два несводимых конфига) — не наш масштаб (Р7 PG, Р11 RLS); иллюстрация антипаттерна «декоративные веса» (родня «декоративным лимитам» из Р10).
- **Версии заметок (5 шт.)** — наш evidence lineage (Р5) строго богаче: не версионирование текста, а происхождение вывода.

### Лицензия

MIT — самый мягкий режим из трёх аналогов (юридически код можно было бы и переиспользовать); README-заявка о коммерческой лицензии файлом LICENSE не подтверждается. По clean-room-конвенции реестра — только идеи, без кода.

## 12.4 Рамка: типология «памяти агента» (Хабр)

**Паспорт.** Не проект, а внешняя типология для стресс-теста покрытия концепции. Источник: habr.com/ru/articles/1046944/ (caveboy, «Почему мы спорим о памяти для AI-агентов», июнь 2026). Тезис: споры о памяти — споры о разных задачах под одним словом; четыре вида памяти + мета-вопросы.

| Вид памяти | Суть по статье | Покрытие Gestalt |
|---|---|---|
| **Документация** | статичные записки (AGENTS.md / MEMORY.md); хороши, пока объём мал; потом — «материал, из которого память предстоит собрать» | вне скоупа по Р15; файлы — не конкуренты, позиционно закрыто |
| **Поиск** | retrieval разрывает связь «масса памяти ↔ объём контекста»; обязан различать актуальное / устаревшее / отменённое / сомнительное | ядро концепции: TTL-предикат + reconciler-свип (Н9 → док 10), supersession = статус, не подавление (Р6), confidence + evidence ≥2 (Р5), valid_time, триаж противоречий (Р6). Закрыто |
| **Состояние работы** | активная задача, гипотеза, статус проверки, затронутые файлы, чекпоинт, причина остановки — «продолжи с того места, где остановились»; трекер хранит статусы, память — незавершённость | **белое пятно → Н11**. Частично: Messages-эпизодика, SESSION-scope, WORLD+PROJECT-факты с коротким TTL, prospective memory Н10(в) |
| **Опыт** | шрамы: отвергнутые пути, причины ограничений, цена компромиссов; «опыт = связи между фактами»; требует отбора против «цифрового чердака» | закрыто: WORLD-факты + conditions + lineage + supersession (отвергнутое сохраняется как reasoning-контекст — Р6); Н4 `permanence=user-asserted`; отбор — TTL + сон |

Мета-вопросы статьи: **путь знания** (кто создаёт / как обновляется / что актуально / как попадает в контекст / что при устаревании) — четыре из пяти закрыто (fast path Р6, усиление/supersession, TTL, soft death + revival); **«как попадает в контекст» — белое пятно → Н1** (слой сборки: отбор, ранжирование, бюджет, префетч). Цена поддержки: закрыто (Р8 pass-once, автоматическая экстракция — против «ручная память недоедает»). Статическая vs динамическая: Gestalt — динамическая.

**Итог стресс-теста**: П1 task-state → Н11; П2 сборка контекста → Н1 (частично Н3 → Р19); П3 ингест внешних источников (AGENTS.md/доки как WORLD-вход) → Н5; мультиагентность — осознанный v2+ (Р3), не пятно.

## 12.5 Cognee (topoteretes)

**Паспорт.** https://github.com/topoteretes/cognee · Topoteretes UG — коммерчески-бэкед open-source (Cognee Cloud, open-core) · 30.4k★, 3k forks, ~9.8k коммитов · Python 3.10–3.14 · лицензия **Apache 2.0** (но production-фича «graph-in-Postgres» — платный продукт; в open-source — demo) · клиенты: Python SDK, MCP (HTTP/SSE/stdio), CLI+UI, Rust/TS, плагин Claude Code · research-бумага: arXiv 2505.24478 (интерфейс KG↔LLM).

**Класс системы.** Пятый в реестре: enterprise memory-платформа «company brain» — ингест любых источников (Drive/Slack/PG/диалоги) → ECL-пайплайн (Extract–Cognify–Load): чанки → LLM-экстракция entity-relationship графа → саммари → эмбеддинги, с провенансом в relational-сторе. Двухуровневая память: session cache (сырые быстрые записи, без экстракции) + permanent KG; `improve()` дистиллирует сессию в граф в фоне. Три хранилища (relational + vector + graph), мульти-бэкенды (Kuzu/Ladybug, Neo4j, LanceDB, pgvector, Qdrant/Chroma/…), multi-tenant: user+dataset = изолированные graph+vector БД, fail-closed с именованием неподдерживаемого бэкенда.

### Что берём

1. **BEAM как внешний бенчмарк → Р14.** Их главный подарок нам. BEAM (arXiv 2510.27246) — внешний бенчмарк разговорной памяти: 10 способностей, почти 1:1 наши мишени: *abstention* = наша контрольная ось C, *knowledge updates* = supersession (Р6), *contradiction resolution* = триаж (Р6), *temporal reasoning* = valid_time, *preference following* = PSYCHE-предсказание (11 §2). Внешний арбитр — ровно анти-PCB-урок из §12.3 (self-benchmark врёт).
2. **Культура отчёта** — подтверждение Р14-в в промышленном исполнении: held-out vs in-sample (10M-результат честно назван «exploratory»), 4–5 повторов полного QA+judge-цикла со std, per-type breakdown, артефакты (конфиги, промпты, прогоны) коммитятся, явная оговорка «public benchmark limits evidence of generalization».
3. **Feedback-weighted retrieval** (`improve()`): элементы памяти, участвовавшие в хорошо оценённых ответах, усиливаются в последующем retrieval. Сигнал — **исход ответа** (rating/acceptance), не факт доступа → снимает напряжение Н10(б) «подтверждение ≠ использование»: усиливать по принятию, не по hit'у.
4. **Двухконтурная интеграция агента** (плагин Claude Code): инжект контекста на UserPromptSubmit, память переживает PreCompact, трейсы инструментов на PostToolUse, финальная дистилляция сессии в постоянную память на SessionEnd — готовый паттерн жизненного цикла для Н1 (сборка контекста) и Н5 (мост ингеста).
5. Микро: тег `_source` в результатах `recall` (session vs graph vs summary) — дешёвая прозрачность происхождения фрагментов для LLM-потребителя.
6. **Диагностический факт.** Слабейшие BEAM-способности при графовом ядре: multi-hop **0.500**, temporal **0.500**, abstention **0.500** (сильные: knowledge updates 1.000, preference following 1.000). Независимое подтверждение Р7 (граф не окупается) и нашей ставки на темпоральность в модели факта (valid_time/supersession), а не в надежде на граф.

### Кандидаты → Н10

- **(д) feedback-weighted retrieval** — усиление элементов памяти по исходу ответа (см. выше; частично пересекается с L3-контуром Р12).
- Слабости BEAM-типов как фильтр для golden-набора: обязательны temporal- и multi-hop-точки — там, где спотыкаются KG-системы.

### Что не берём

- **KG-центричность** (entity-relationship экстракция как ядро памяти) — Р7; их же multi-hop 0.500 при графовом ядре. Наш мир — факт с lineage, не граф сущностей.
- **Мульти-бэкенд-зоопарк** (десяток векторных/графовых бэкендов) — анти-Р7; их собственный PG-only pivot — косвенное признание (но production-версия у них платная; мы делаем pure-PG ядром сразу).
- **Open-core монетизация** — чуждая модель; для нас маркер рынка, не паттерн.
- **AUTO_FEEDBACK** (один LLM-вызов после *каждого* запроса на self-tune памяти) — нарушение Р8 (batch-amortized); правильная форма того же сигнала — feedback-веса в батче (п. 3).
- **Session cache как отдельное хранилище** (Redis/PG cache backend) — паттерн двухуровневости берём (Н5/Н1), реализацию — нет: у нас эпизодика = Messages в PG, fast/slow — дисциплина приёма (Р6), не второй стор.
- **«Cognitive-science-grounded ontology»** — типы сущностей ≠ идиографика (иллюстрация Р4): модели человека в Cognee нет вовсе, «память» = корпоративное знание. Ближайший аналог по инфраструктуре, не по предмету.

### Лицензия

Apache 2.0 — самая свободная из реестра (код legally заимствуем), но по clean-room конвенции — только идеи. BEAM-датасет и рубрики — открыты (HuggingFace, arXiv) — прямой кандидат в нашу метрику (Р14).

## 12.6 Пилотный стенд памяти (прототип v0)

**Паспорт.** Собственный пилотный стенд автора (прототип v0) · Java 21, zero-framework (com.sun.net.httpserver + виртуальные потоки), Gradle, Docker, :8010 · бэкенд: Honcho only (:8000) · транспорт: MCP stateless Streamable HTTP (POST /mcp) + REST /memory/{enrich,block,track,save,find} · интеграция: плагин агент-хоста — thin shim (256 строк, вся логика в сервисе) · ежедневная эксплуатация с 2026-08.

**Класс системы.** Шестой в реестре: personal memory-infrastructure — интеграция с агент-хостом (события хоста: chat.message/transform/compacting/session-*) + сервис-обёртка над внешним движком. Функциональный предок Gestalt (по Р15 — без обязательств), с особым бонусом: это и есть «датасет пилотного стенда» из Н2 — золотой источник данных для golden-набора (Р12).

**Эволюция как главный урок.** MIGR-1 (уход от внешнего плагина) → MIGR-2 Graphiti (three-tier routing #global/#user → group_id) → EVOL-2 (routing/targets API) → MIGR-3 Cognee (Graphiti «not production-ready»: 18 с/conclusion, silent-fail) → брошен на Stage 2 → Honcho-only. **Три смены facts-бэкенда за месяц ради задачи «разложить тексты по тирам»** — потому что у conclusion нет модели факта: tier — свойство данных, и у нас это `scope` (Р13), а не бэкенд и не тег.

### Что берём (проверено эксплуатацией)

1. **Thin-shim контракт интеграции** — плагин только связывает события и не содержит логики: обновление сервиса не требует обновления плагина → паттерн для Н1/Н5. Клиентские таймауты = 2× серверного бюджета.
2. **Блок как интерфейс памяти** — агент потребляет не сырой поиск, а собранный блок из 5 секций с бюджетом (`maxBlockChars`), приоритизацией секций, sync-deadline 2 с + async-прогрев кэшей → полевое подтверждение П2 (PortraitSnapshot → **Р19**); дедлайн/бюджет — паттерны для Р19 (coalescing в Р19 поглощён джобой перестройки).
3. **Enrich-coalescing** — per-session state, latest-wins, очередь ≤5: частые сообщения не множат работу → паттерн Encoding-батчей (Н5/ТЗ).
4. **Hints-аккумулятор** (topics → recall → summarize → FIFO, дедуп по темам и по «заявленным» выводам) — прообраз слоя сборки контекста → Н1. Идемпотентность topics-кэша по fingerprint(llm+text) — дешёвый инвариант против повторных LLM-вызовов → Н1.
5. **Производственная закалка**: Caffeine fail-open (провалившийся loader не кэшируется — транзиент не отравляет), Retrier на транзиентные 500, срез по границе слова при trim, observability-заготовки.
6. **B-plus sharedObserverPeer** — все ассистенты одним пулом наблюдения, атрибуция тегами — примитивная, но живая реализация наблюдателя (Р3, квадрант AU).

### Кандидаты → Р19/Н1

- Prewarm блока (сейчас первый ход холодный — EVOL-1 Stage 1 не закрыт) → в Р19 поглощён джобой Reconciliation (профиля всегда готов); паттерн актуален для ингеста/Encoding → Н5.
- Coalescing + topics-fingerprint (см. выше).

### Что не берём / дефекты (Gestalt чинит)

- **Нет факт-модели** — conclusion = плоский текст без owner/domain/scope/conditions/lineage → вся сага тиров; корневой дефект, из него остальные.
- **Routing-теги в контракте агента** — `#global`/`#user` умерли дважды (MIGR-2 ввёл → MIGR-3 убрал), а контракты их всё ещё обещали: документация юзера (описание: «префикс strip'ается до записи») и описание MCP-инструмента («Supports #global or #user prefixes») — при этом код хранил verbatim («routing prefixes are plain text»). Урок: **routing — свойство факта в сервисе (Р13), не тег в контракте агента**; агентские контракты дрейфуют от кода, когда декларируют поведение, которого нет.
- **LLM в read-path** — selfReflection/userSummary = peer_chat-вызовы Honcho при каждом прогреве; hints-суммаризация LLM на каждый батч — анти-Р8 (тяжёлая работа от сырых данных); наш слепок O(1).
- **Honcho как единственный стор**: save 20–60 с (синхронный embedding), find — спорадические 500 → Р7 (pure-PG снимает).
- **sessionKey per-directory** — «сессия» памяти склеивает все сессии проекта в агент-хосте, Message-идентичности нет, compact грубый → Р11 (иерархия User→Project→Session→Message).
- **tool_result-загрязнение** ингеста (инвариант EVOL-1 Stage 3 не восстановлен) → фильтры fast path (Р6).
- **localhost без изоляции** — tenant override заголовками из любого локального процесса → Р11 (RLS).
- **Ноль метрик** — работает ли блок, не измеряется; единственная обратная связь субъективна → Р12/Р14.

### Лицензия

Собственный код автора — ограничений нет; использование как источника паттернов и данных (golden-набор) свободно.
