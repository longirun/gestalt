# 18 — Теоретическая оценка производительности концепции (v1)

> 2026-09-06 · Статус: **теоретическая (модельная) оценка**, не измерения и не бенчмарк.
> Метод: анализ вычислительной сложности и модельных объёмов по канонам (06–17); все числа — порядки величин из поведенческой модели целевого режима (B2D, Р26: один активный юзер-разработчик, ежедневная работа с агент-хостом).
> Проверка оценки — NFR-прогоны в ТЗ (Н8) и метрика (11); косвенные валидации — §6.
> Это анализ, не решение: строка реестра не заводится (как у 05.2).

---

## 1. Постановка и главный тезис

**Вопрос.** Потянет ли Pure PostgreSQL (Р7) концепцию v1 хотя бы для одного пользователя? Не превратится ли система в неповоротливого монстра, где каждый Dreaming идёт сутками?

**Главный тезис.** Производительность концепции определяется не СУБД, а **LLM-дисциплиной** — и она уже зашита в инварианты: pass-once + batch-amortized (Р8), 0 LLM в дедупе (Р6), 0 LLM в read-path v1 (Р19), вычислимая важность без LLM (Р30). PostgreSQL-ядро в целевом режиме имеет **2–3 порядка запаса** до комфортной зоны; суточный Dreaming невозможен по построению — в системе нет ни одного full-scan-процесса (§4).

Оценка сознательно консервативна: берём верхние края модельных объёмов.

## 2. Карта нагрузки по канону 13

| Контур | Каденция (06 §Q2) | Вход | LLM | SQL-профиль |
|---|---|---|---|---|
| **Encoding** | секунды | work-unit ≥512 ток., age-flush 1800 с (Р6) | 1 вызов на батч | identity-lookup по индексу; reinforcement = UPDATE (16 §3.1) |
| **Dreaming** | часы | очереди кандидатов (write-time), закрытые сессии | пара батчей на прогон | точечные статусы, recursive CTE по цепочкам |
| **Gestalting** | дни | свежие PSYCHE-атомы, emerging-кандидаты | только именование оси (09: вход 5–10 фактов) | кластеризация по косинусу на свежем срезе |
| **Reconciliation** | фон | TTL-свипы, judge-батчи словарей (Р25), перестройка слепка | judge — только на кандидатах склейки | индексные сканы, лимитированный drain |
| **Read-path** | на запрос (API вне ядра, Р18) | PortraitSnapshot + WORLD-recall | **0** (Р19) | O(1) чтение слепка; Top-K ANN/FTS |

Ключевой столбец — «Вход»: **ни один контур не перечитывает сырые диалоги** (Р8). Тяжёлая работа всегда от хранимых фактов, а факты прирастают потоково, значит объём работы пропорционален потоку опыта, а не размеру базы.

## 3. Модельные объёмы (1 юзер, год эксплуатации)

Допущения о поведении: 50–200 сообщений/день (активная разработка с агент-хостом), доля сохраняемых фактов после дедупа ~0.2–0.3 на сообщение (эмпирика класса — Honcho, §12.2: ~0.2–0.3 вызова/сообщение).

| Сущность | Порядок/год | Вес | Примечание |
|---|---|---|---|
| Messages | 20–70k строк | сотни МБ с индексами | никогда не умирают (10 §5) |
| Facts (все статусы) | 5–20k строк | десятки–100 МБ | вектор 1536d ≈ 6 КБ/шт; ACTIVE — меньшая часть |
| ConstructAxis / Instance | десятки–сотни / тысячи | единицы МБ | словарь осей насыщается (09) |
| PortraitSnapshot | ≤40×200 × 3 секции | килобайты | материализованная проекция (14) |

**Итого: < 1 ГБ/год.** Комфортная зона PG — миллионы строк и десятки ГБ; по строкам запас ~2 порядка, по векторному индексу (HNSW на тысячах векторов против рабочих миллионов) — 3 порядка. Индексы 16 §3.1 на таких объёмах деградации не имеют.

## 4. Оценка по контурам: почему Dreaming не сутки

### 4.1 Read-path (горячий путь)

- **Слепок — O(1)**: готовый текстовый блок (Р19, канон 14). Юзер всегда на готовом профиле; инвалидация — предикат `max(system_time входов) > cutoff` (события write-path ничего не пишут).
- **WORLD-recall — Top-K** по partial ACTIVE-only индексам (HNSW/FTS, 16 §3.1) — миллисекунды на векторных объёмах §3.
- **Ранжирование с весом w** (17 §5): экспонента — тривиальная арифметика инлайн в ORDER BY. Δопыт = count сессий пула с `last_seen` — индексный count. Единственный кандидат на денормализацию — **монотонный счётчик сессий пула** (вместо count при каждом ranking) → ТЗ (Н8).
- Snapshot-джоба (дефолт 10 мин): пересбор по ≤40×200 входов — суб-секундная, 0 LLM.

### 4.2 Encoding

Батч-амортизация: 1 LLM-вызов на work-unit, anchor рождается в том же вызове (+~50% output-токенов на факт, 0 отдельных вызовов — 16 §2.2). SQL — identity-lookup по уникальному составному индексу (O(log n), микросекунды–мс) и UPDATE без INSERT при дедуп-попадании. Дедуп детерминирован — 0 LLM (Р6).

### 4.3 Dreaming

Стоимость пропорциональна **очередям кандидатов, а не базе**: supersession/merge-кандидаты рождаются на write-time при промахе дедупа (16 §4.1), пост-мортем сон — только по закрытым сессиям (TTL-предикат + reconciler `closed_at`, 10 §5). Десятки кандидатов на прогон → **секунды SQL + пара LLM-батчей**. Recursive CTE по supersession-цепочкам — O(длины цепочки), цепочки короткие (5–20 хопов).

### 4.4 Gestalting

Индукция кластеризует **только свежие атомы** (прирост с прошлого прохода), position детерминирован из evidence; LLM — только именование оси: короткий вызов на 5–10 фактов (09). При десятках–сотнях осей на юзера это единицы–десятки вызовов в месяц.

### 4.5 Reconciliation

TTL-свипы и `closed_at` — индексные фоновые сканы. Judge-батчи словарей — только на кандидатах склейки (после стабилизации словарей — единицы пар в неделю на проект, Р25), лимиты по времени/объёму, drain-режим, lease+backoff+poison (Р10). Перестройка слепка — §4.1.

### 4.6 Адресная история (Р29)

Exact по anchor — полный GIN(anchor) (16 §3.1), миллисекунды. Навигация вниз от ACTIVE по `superseded_by_id` / от сводного к атомам по `generalized_from` — мелкохоповые цепочки (Р7: 90% графовых workload'ов). Temporal query-side — Н5, soft-dependency. История вне семантического горячего набора — heavy-индексы её не содержат, деградации горячего пути нет.

### 4.7 Профилирование агентов и метрика (07, 11) — вне рантайм-нагрузки

Матрица AU (07): пассивная экстракция тем же Encoding-проходом — **0 дополнительных LLM-вызовов**; пиннинг эпох — метаданные. Метрика (11): офлайн golden-набор в CI (L1/L2, 100–300 точек) + онлайн L3 acceptance-rate из событий kill-insight/acceptance — оба контура не нагружают живой read/write-path.

## 5. Дефицитные ресурсы и настоящие потолки

1. **Главный дефицит — LLM-токены, не PG.** Экстракция, судьи, именование — единственные платные операции; их поток уже дисциплинирован (Р8 pass-once; Р6 батчи; Р25 drain). Стоимость растёт линейно потоку опыта и не зависит от размера накопленной базы — это прямое следствие инварианта «тяжёлая работа от фактов, не от диалогов».
2. **PG-потолок — мультитенант v2+** (Р20): 100M+ фактов → партиционирование по owner, квантизация векторов (halfvec/binary pgvector), per-tenant частичные индексы. Escape-путь заложен SPI GraphStore (Apache AGE опция / Neo4j enterprise, Р7) — смена хранилища без смены ядра.
3. **v2-фича, отмеченная как дорогая**: непрерывная интерференция полюсов (17 §7) — агрегаты на сессию/полюс, дороже в SQL, поэтому v2; но lineage конструкта — десятки строк, сам агрегат дешёв.
4. **Анти-паттерны, исключённые концепцией по построению**: reprocessing сообщений (Р8), глобальные пересборки словарей («не существует» — Р25), stored-priority (Р30), LLM в дедупе и read-path (Р6/Р19), full-scan фоновые джобы (все контуры работают очередями кандидатов).

## 6. Косвенные валидации и их границы

- **Пилотный стенд §12.6**: блок-интерфейс с бюджетом/дедлайном/coalescing жил в ежедневной эксплуатации (с 2026-08) на PG-бэкенде без деградации. Оговорка: стенд — сервис-обёртка над Honcho, не pure-PG ядро; валидированы интерфейсные паттерны (поглощены Р19/Р8), а не ядро.
- **Honcho (§12.2)**: production-прецедент того же класса нагрузки — single-pass deriver над PG/pgvector, работа от хранимых фактов. Подтверждает класс, не нашу схему.
- **Эмпирика живой базы (Р25)**: порог косинуса 0.85, доменные доли — порядки величин для NFR, не канон.

Прямых измерений ядра нет — ядро не реализовано; потому документ и заявлен как теоретическая оценка.

## 7. Выводы и переход в ТЗ (Н8)

1. Для целевого режима v1 (1 юзер, B2D) **PG-ядро имеет 2–3 порядка запаса**; «суточный Dreaming» исключён построением (инвариант очередей кандидатов против full-scan).
2. Бутылочное горлышко — **LLM-токены**; их поток линеен потоку опыта и уже ограничен инвариантами Р6/Р8/Р25.
3. В ТЗ (Н8) уходят инженерные детали, подтверждённые этой оценкой как единственные нетривиальные:
   - **денормализованный монотонный счётчик сессий пула** для Δопыт (иначе — count при каждом ranking);
   - NFR-пороги 16 §3.1 (латентности горячего набора, размеры батчей);
   - дефолты каденций джоб (Dreaming — часы, snapshot — 10 мин, Gestalting — сутки) — конфиг.
4. Пересмотр оценки — при срабатывании триггеров v2 (мультиаренда, Р20) или при NFR-замерах на реализованном ядре.
