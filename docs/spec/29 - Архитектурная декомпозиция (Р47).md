## 1. Модульный состав

- **Упаковка ядра:** zero-framework core (Р17) — максимальная тестируемость (тысячи unit-тестов, Р36).
- **Хранилище v1:** Pure PG 16+ напрямую (Р7; GraphStore SPI — v2+, Н15).
- **Модули:** `core` (доменное ядро), `reconciler` (демон фоновых задач), `server` (API), `starters` (автоконфигурации Spring Boot / Micronaut; Р17).
- Границы и зависимости модулей не закрыты — §1.1, §5 (фаза ТЗ).

### 1.1. Инфраструктурные зависимости и изоляция (первый взгляд, для проработки в ТЗ)

Разрешение дилеммы между «встраиваемостью (embed без dependency hell)» и «энтерпрайз-надёжностью (пулы коннектов, ретраи, маскирование)» — разделение ответственности по модулям через инверсию управления:

*   **`gestalt-core` (Zero-framework, Embed-ready):**
    *   **БД:** инверсия управления через стандартный `javax.sql.DataSource` (`java.sql`) вместо прямого `DriverManager`. Ядро не тащит жесткую зависимость на пул соединений (HikariCP и др.) — JVM-хост передаёт свой настроенный `DataSource` (с пулом, метриками и транзакциями хоста).
    *   **Логирование:** абстракция `System.Logger` (нативный Java 9+) или легковесный `slf4j-api` (без привязки к реализации). Маскирование sensitive-данных (токены, PII) конфигурируется на уровне логгера хоста (Logback, Log4j2).
    *   **HTTP / LLM:** нативный `java.net.http.HttpClient` (Java 21, на виртуальных потоках Loom) с компактным декоратором политик устойчивости (exponential backoff + jitter, таймауты) либо вынос за тонкий `LlmProvider` SPI (§5). Никаких тяжелых HTTP-библиотек в ядре.
*   **`gestalt-server` (Standalone / Sidecar / Docker-образ):**
    *   Готовый микросервис для не-JVM хостов (Python, TypeScript) и multi-service развёртывания.
    *   Включает полную production-обвязку: HikariCP, REST/MCP API, готовый логгер с маскированием, Micrometer метрики, healthchecks, миграции Flyway.
*   **`gestalt-spring-boot-starter` (и др. стартеры):**
    *   Автоконфигурация для быстрого подключения `gestalt-core` в JVM-бэкенд: подхват контекстного `DataSource`, маппинг `application.yml` в конфиг ядра.

## 2. Провайдер эмбеддингов (`EmbeddingProvider` SPI)

Вычисление векторов вынесено за SPI-порт (Java SPI, Р17). Ядро знает только контракт.

### 2.1. Контракт SPI

*   **Метаданные модели** — один раз при инициализации: идентификатор модели и размерность; ядро кэширует для валидации пиннинга и создания индексов.
*   **Batch-эмбеддинг** — список текстов → список векторов. Write-path (Encoding) и фон (Reconciliation: консолидация словарей, Р25). Латентность не критична.
*   **Single-эмбеддинг** — один текст → один вектор. Read-path (recall: эмбеддинг запроса). **Латентно-критичный** — горячий путь пользовательского запроса; целевой бюджет < 50 мс.

### 2.2. Пиннинг модели на базу

Векторы разных моделей математически несравнимы:

1.  При первой инициализации ядро записывает `(model_id, dimensions)` в системную таблицу `gestalt_meta`.
2.  При последующих стартах ядро сверяет ответ провайдера с записью.
3.  **Несовпадение = отказ старта** (не тихая деградация — нарушение целостности данных). Смена модели — явная миграция с пере-эмбеддингом всей базы.
4.  Следствие (Р25): **пороги косинусного сходства** (0.85 — кандидаты склейки словарей, 0.90 — NARRATIVE-дедуп 16 §4.1) **привязаны к модели** — при смене требуют перекалибровки.

### 2.3. Паттерны использования по контурам

| Контур | Вид вызова | Латентность | Примечания |
|---|---|---|---|
| **Encoding** (write-path) | batch | Не критична | Эмбеддинг `statement` для HNSW-вставки и семантического дедупа (16 §4.1) |
| **Dedup** (write-path) | — | — | Переиспользует вектор, вычисленный выше (0 дополнительных вызовов) |
| **Surprisal** (Р38) | — | — | `1 - max_sim` — переиспользует тот же вектор (0 дополнительных вызовов) |
| **Recall** (read-path) | single | **< 50 мс** | Эмбеддинг запроса для HNSW-поиска в Канале Б (§3) |
| **Reconciliation** (background) | batch | Не критична | Консолидация словарей: косинус строк-кандидатов (Р25) |

**Pass-Once (Р8):** вектор факта вычисляется один раз — дедуп и surprisal переиспользуют его без дополнительных вызовов провайдера.

### 2.4. Реализации v1

| Реализация | Дефолт | Размерность | Ориентир модели | Языки |
|---|---|---|---|---|
| **Remote-API** (HTTP, OpenAI-совместимый) | ✅ | 1536 | `text-embedding-3-small` | Мультиязычная |
| **In-JVM ONNX** (int8, ~22–33 МБ) | ❌ | 384 | `all-MiniLM-L6-v2` / `e5-small-v2` | EN (ограниченно RU) |

*   **Remote-API** — нулевая конфигурация: ключ API + endpoint. Дефолт v1, опора схемы (16 §3: `1536d`).
*   **In-JVM ONNX** — enterprise / air-gapped: модель — ресурс артефакта, int8-квантование (~десятки МБ). Компактные модели (384d) слабее на мультиязычных данных — для RU-контента рекомендуется Remote-API.
*   Размерность `embedding`-колонки в PG определяется провайдером при первом старте. Смена реализации с другой размерностью = миграция (тот же пиннинг).

### 2.5. Деградация вместо отказа (fail-open)

*   **Без векторов работает:** точный дедуп (identity-lookup, B-Tree/GIN по anchor), навигация по `superseded_by_id`, FTS (GIN tsvector).
*   **Write-path при отказе провайдера:** факт записывается без вектора, встаёт в очередь до-эмбеддинга; до восстановления участвует только в exact-дедупе и FTS.
*   **Read-path при отказе:** деградация до FTS-only (лемматизация) — полнота падает, система не отказывает.
*   Итог: недоступность провайдера = **просадка полноты, не отказ системы** (ADR спайка 24 §9).

## 3. Read-path API (`ContextProducer` v1)

**Паттерн: Dual-Path Tiered Assembly** (06 §8.2): standing context + динамический recall — два независимых канала поставки. Канал А (PortraitSnapshot: секции, капы, формат инжекции, контракт поставки — бюджет блока/sync-deadline/fail-open) — канон **14 §2–3, §6**; здесь — только архитектурные решения поверх канона.

### 3.1. Канал Б: Dynamic WORLD-Recall (Top-K по запросу)

Детерминированный поиск фактов по явному запросу потребителя (контракт Р35 — 14 §6):

*   **Multi-signal retrieval:** dense semantic (pgvector HNSW) + BM25 keyword (GIN tsvector, лемматизация) + entity-boost (по живому словарю Р25). Паттерн подтверждён Mem0 v3 (реестр 12).
*   **Temporal query-side:** классификация временного намерения запроса («сейчас» vs «на прошлой неделе» vs «в будущем») → фильтрация по `valid_time` / `event_date`. Механика — структурированные фильтры `recall()`, не LLM в движке.
*   **Возврат:** Top-K фактов (K — конфиг → ТЗ, Н8) с провенансом (проект-источник, сессия, время). Слабый сигнал — тишина (no-false-memory, Р14). Multi-hop — агентная петля tool-call'ов, не движковая фича.
*   **Радиус:** дефолт = context(S) (10 §3.3); USER-радиус (кросс-проектный) — явный параметр (Р35).

### 3.2. Режимы потребления

| Режим | Кто формулирует запрос | Что получает хост |
|---|---|---|
| **inject** (standing context) | Никто (безусловно) | Слепок в системном промпте каждого хода |
| **tool** (function calling) | Хост-LLM через tool-call `recall()` | Top-K фактов с провенансом (Р35) |
| **inject + tool** (полный) | Оба | Слепок + результаты recall |

Хост без tool-loop получает только standing context. Формулировка запроса — обязанность потребителя (semantic gap закрывается в уже идущем инференсе хоста, Р35).

### 3.3. v2+ (двери открыты)

LLM-микс (суммаризация результатов recall), агентный цикл дедукции (паттерн Honcho Dialectic), бюджетная лестница стратегий, пайп-режим (детерминированное разворачивание контекста по Messages для хостов без инжекта и tool-loop — Р35, проверка против буквы Р8). Механизмов в v1 не строим; API v1 не закрывает дверь (стратегия `ContextProducer` — точка расширения).

## 4. Внешние адаптеры ингеста

Gestalt — middleware: ядро не управляет сессиями агента, а принимает данные от хоста через тонкий адаптер. Адаптер — единственная точка связи хоста и движка памяти.

### 4.1. Принцип thin-shim (полевой урок §12.6)

Адаптер **только связывает события хоста с API движка** и не содержит бизнес-логики. Вся обработка (экстракция, дедуп, сборка контекста) — внутри ядра. Следствие: обновление ядра не требует обновления адаптера; адаптер — десятки–сотни строк, а не фреймворк.

### 4.2. Двухконтурная интеграция (паттерн §12.5 Cognee, §12.6 стенд)

Адаптер подключается к хукам жизненного цикла агентского хоста:

| Хук | Что делает адаптер | Контур |
|---|---|---|
| **SessionStart** | Регистрирует сессию, запрашивает standing context (слепок) | Read |
| **UserPromptSubmit** | Инжектирует standing context + результаты `recall()` в системный промпт | Read |
| **AssistantResponse** | Отправляет пару (user message, assistant response) в Encoding (батч, Р6) | Write |
| **PostToolUse** | Отправляет агентные подтверждения действий в Encoding | Write |
| **SessionEnd** | Сигнализирует закрытие сессии; движок финализирует батч, тикает счётчик опытного времени (17 §4) | Write |

Не все хуки обязательны. Минимальная интеграция: `AssistantResponse` (write) + `UserPromptSubmit` (read).

### 4.3. Фильтрация `tool_result` (Р3; 07 §5 п.7)

Критерий — атрибуция: **ингесту подлежат только реплики Actor'ов** (`kind: PERSON | AGENT`, Р3); сырой вывод инструмента — машинный артефакт, не наблюдение. Агентские подтверждения действий — ценный first-class вход (+51.8 assistant-recall на LongMemEval, §12.7).

| Источник | Пример | Действие |
|---|---|---|
| Реплика юзера | «используй порт 5433 для прода» | ✅ Ингест |
| Реплика агента (подтверждение действия) | «я создал файл config.yml с портом 5433» | ✅ Ингест |
| Реплика агента (рассуждение) | «давайте подумаем, какой порт подойдёт…» | ✅ Ингест |
| Сырой `tool_result` | `{status: 200, body: ...}` / `ls -la` дамп | ❌ Фильтр |

Адаптер маркирует каждую реплику атрибуцией (`user` / `assistant` / `tool_result`); ядро по умолчанию принимает только первые два вида.

### 4.4. Модели деплоя

| Модель | Описание | Когда |
|---|---|---|
| **Библиотека (embed)** | Ядро — зависимость в проекте хоста; адаптер — вызов API в процессе | Хост на JVM (Spring Boot, Micronaut); минимальная латентность |
| **Sidecar (localhost)** | Ядро — отдельный процесс; адаптер — HTTP/MCP-клиент | Хост не-JVM (Python, TypeScript); изоляция |
| **Hosted API** | Ядро — удалённый сервис; адаптер — тонкий HTTP-клиент | Multi-tenant, SaaS (v2+, Р11) |

В v1 — библиотека (embed) + sidecar. Hosted API — v2+ (Р11).

### 4.5. Связь с Encoding

Адаптер — **поставщик сырых данных**; вся обработка — в ядре:

```
Адаптер (thin-shim)          Ядро (Encoding pipeline, Р6)
─────────────────────        ─────────────────────────────
событие хоста
  → атрибуция (user/assistant/tool)
  → маркировка (session_id, project_id)
  → отправка в ядро ────────→ батч-буфер (токен-батчинг + age-flush)
                               → LLM-экстракция фактов
                               → двухшаговый дедуп (Р23)
                               → запись в PG
```

Адаптер не парсит реплики, не извлекает факты, не решает конфликты. Его обязанность — **атрибуция** (кто сказал), **маркировка** (в рамках какой сессии/проекта) и **доставка** в ядро.

## 5. Незакрытое (наполнение при ТЗ, Н8)

- границы и зависимости модулей (`core` / `reconciler` / `server` / `starters`) — диаграмма и правила изоляции;
- **`LlmProvider` SPI** — контракт LLM-вызовов ядра (экстракция, naming, judge) — аналог `EmbeddingProvider`; в v1 не специфицирован;
- изоляция хранилищ: RLS/партиционирование (Р11) — инженерная проработка;
- конфигурация (иерархический конфиг со снапшотом, Р10) и observability;
- поверхность `server` API;
- числовые дефолты: K Top-K, бюджет блока, порог Δ директив, SLA латентности read-path.
