## 1. Назначение и концептуальное место

В концептуальном фундаменте Gestalt память разделена по таксономии Тульвинга на три ортогональных слоя:
1. **Эпизодика (`Message`):** сырые логи диалогов («что и когда было сказано»).
2. **Семантика мира (`Fact/WORLD`):** точные наблюдаемые данные о мире, включая пользователя как физический объект мира («что существует и истинно в мире»).
3. **Модель человека (`Fact/PSYCHE` + `Construct`):** интенциональная ToM-модель профессионального почерка и смысловых осей инженера («как и почему он мыслит»).

Если домен `PSYCHE` опирается на теорию личностных конструктов Келли (`09 - Construct.md`), то домен `WORLD` — это **классическая семантическая инженерия знаний (Knowledge Representation)** с би-темпоральностью, строгим скоупингом и гибридным извлечением.

Факты мира («проект на Java 21 LTS», «порт базы 5432», «отказались от JPA в пользу jOOQ») принципиально **не являются конструктами Келли**:
- У них нет биполярных полюсов («Java 21 vs что?» — это абсурд).
- Они не отражают внутреннюю шкалу ценностей человека, а фиксируют внешнее состояние среды.
- Однако они служат **условиями (`conditions`)** для конструктов и сырьём для индукции ToM-портрета.

Настоящий документ определяет, как хранить точные данные мира, как управлять их жизненным циклом при накоплении тысяч записей (anti-mess) и как доставлять их в контекст агента без его переполнения.

## 2. Онтология и модель сущности `Fact`

Каждый факт в системе однозначно позиционируется в трёхмерном пространстве (**Р13**):
$$\text{Fact} = \langle\text{owner}, \text{domain}, \text{scope}\rangle$$

- `owner` — пользователь (Actor `PERSON`). Бесхозных фактов не бывает.
- `domain = WORLD` — онтологическая категория (наблюдаемое о мире).
- `scope ∈ {SESSION, PROJECT, USER}` — радиус релевантности внутри владельца (`10 §3.1`).

### 2.1 Схема сущности `Fact`

```
Fact {
  // 1. Идентификация и адресация
  id: UUIDv7,                           // Time-ordered первичный ключ
  owner_id: UUID,                       // Владелец (User)
  domain: WORLD,                        // Доменная категория (Р13)
  scope: SESSION | PROJECT | USER,      // Радиус релевантности (Р13)
  project_id: UUID?,                    // Nullable: привязка к проекту (10 §3.1)

  // 2. Семантическое содержание
  statement: String,                    // Человекочитаемое утверждение для LLM и векторизации
                                         // («Проект gestalt разрабатывается на Java 21 LTS»)
  sort: STATE | NARRATIVE | EVENT,      // Сорт факта — природа содержания; задаёт
                                         // обязательность полей anchor (§2.2)
  anchor: {                             // Структурированный якорь (EAV-триплет)
    subject: String,                    // «gestalt» — обязателен для всех сортов
    predicate: String?,                 // «runtime.version» — обязателен только для STATE
    object: String?                     // «Java 21 LTS» — обязателен только для STATE
  },

  // 3. Би-темпоральность (Снодграсс, Р5)
  valid_time: [Timestamp, Timestamp?),  // Интервал истинности в мире (t_end = null -> актуален)
  transaction_time: Timestamp,          // Время физической фиксации в Gestalt

  // 4. Статус и история (SCD Type 2, Р6)
  status: ACTIVE | SUPERSEDED | RETIRED,
  superseded_by_id: UUID?,              // Ссылка на факт-преемник

  // 5. Эпистемический вес и провенанс
  confidence: Float,                    // Доверие [0.0 .. 1.0]
  reinforcement_count: Int,             // Счётчик независимых подтверждений (Р10)
  last_seen_at: Timestamp,              // Время последнего упоминания / подкрепления
  lineage: [UUID],                      // Ссылки на исходные Message.id

  // 6. Политики приоритизации
  is_critical: Boolean,                 // Маркер инварианта -> попадает в PortraitSnapshot.CRITICAL
  permanence: INFERRED | USER_ASSERTED  // Явное «запомни навсегда» от юзера -> защита от TTL
}
```

### 2.2. Сорта фактов и обязательность anchor

Два независимых измерения факта, которые не следует путать:

- **anchor** (§2.1) — *форма записи*: триплет `subject → predicate → object`, адресуемая часть факта;
- **sort** — *природа содержания*: каким по сути является факт. Сорт определяет, насколько полным
  обязан быть anchor; anchor не определяет сорт.

| Сорт | Природа | Примеры | Обязательность anchor |
|---|---|---|---|
| **STATE** | состояние/свойство мира: значение, версия, порт, путь, зависимость, имя, конфигурация | «проект на Java 21 LTS», «порт базы 5432», «зависимость jOOQ» | полный: subject + predicate + object — **обязателен** |
| **NARRATIVE** | решение, договорённость, причина, контекст выбора | «отказались от JPA в пользу jOOQ из-за N+1» | частичный: subject [+ predicate]; смысл живёт в `statement` |
| **EVENT** | инцидент, происшествие, эпизод мира | «хост упал от OOM в 3 ночи» | вырожденный: subject; identity — `valid_time` |

Правила:

1. **Полный anchor обязан только STATE.** Принуждение экстрактора триплетировать всё порождает
   выдуманные предикаты для NARRATIVE/EVENT (predicate sprawl — аналог axis sprawl, Н4) и разрушает
   дедуп/supersession по `(subject, predicate)`.
2. **Exact-дедуп (§4.1) применяется только к фактам с полным anchor** (STATE); NARRATIVE/EVENT
   дедуплицируются семантической веткой (косинус).
3. Сорт проставляет экстрактор в том же батч-вызове Encoding (Р6): один enum-токен на факт —
   отдельных вызовов LLM и заметного расхода токенов сорт не добавляет.

## 3. Физическое хранение: Pure PostgreSQL 16+ (**Р7**)

Хранилище домена `WORLD` строго консолидировано в единой PostgreSQL-базе без привлечения внешних специализированных графовых или векторных СУБД.

```
                  ┌────────────────────────────────────────────────────────┐
                  │                 PostgreSQL 16+ (Р7)                    │
                  ├────────────────────────────────────────────────────────┤
                  │  Таблица: `facts`                                      │
                  │  ├── B-Tree: (owner_id, domain, scope, project_id)     │
                  │  ├── JSONB / GIN: anchor (subject, predicate, object)  │
                  │  ├── pgvector (HNSW): embedding (statement, 1536d)     │
                  │  └── tsvector / GIN: fts_tokens (lexemes statement)    │
                  └────────────────────────────────────────────────────────┘
```

1. **Таблица `facts`:** хранит все атрибуты записи.
2. **Точные термины (`tsvector` + GIN):** полнотекстовый индекс с русской и английской лемматизацией. Критически важен для инженерного домена: поиск точных версий (`Java 21`), названий библиотек (`HikariCP`, `jOOQ`), номеров портов (`5432`) и параметров конфигурации. Векторные модели часто «размывают» такие токены в абстрактные понятия; FTS даёт 100% точное попадание.
3. **Семантика (`pgvector` + HNSW):** векторное представление текстового поля `statement` для неточных смысловых запросов («как у нас устроена работа с базой данных?» $\to$ подъём факта про Postgres и пул соединений).
4. **Структурные предикаты (JSONB + GIN):** быстрый индекс по полям `anchor`, позволяющий детерминированно находить существующие факты по объекту и предикату без вызова LLM.

### 3.1. Инварианты горячего набора (анти-деградация)

Память растёт годами — поиск деградировать не должен. Два инварианта хранения:

1. **Поисковые индексы сигналов — только ACTIVE** (partial indexes `WHERE status = 'ACTIVE'`):
   HNSW (`embedding`), GIN (`fts_tokens`) и GIN (`anchor`) не индексируют историю SUPERSEDED/RETIRED —
   размер горячего набора ограничен живыми фактами независимо от накопленной истории.
   Служебные B-Tree (адресация, scope-фильтры) — полные.
2. **Reinforcement — UPDATE строки, а не INSERT** (§4.1): подтверждение уже известного факта
   инкрементит счётчик и не трогает тяжёлые индексы — повторы не разбухают HNSW/GIN.

Количественные пороги (p99, бюджеты индексов, параметры HNSW) — NFR, имплементационные детали → ТЗ (Н8).

## 4. Жизненный цикл и гигиена: борьба с хаосом (Anti-Mess)

Когда в системе накапливаются тысячи фактов, неконтролируемый рост предотвращается на каждом этапе конвейера памяти:

### 4.1. Fast Path (Encoding): Дедупликация и усиление счётчиком (**Р6, Р10**)
- **Проблема аналогов:** при каждом упоминании факта создавать новую строку в БД или гонять LLM для слияния (Mem0/Honcho).
- **Решение Gestalt:** 
  1. Извлечённый факт-кандидат проверяется по базе детерминированно:
     $$\text{exact\_match}(anchor) \quad\lor\quad \cos(\vec{v}_{new}, \vec{v}_{existing}) \ge 0.90$$
     Exact-ветка применима только к фактам с полным anchor (STATE, §2.2);
     NARRATIVE/EVENT — только семантическая ветка.
  2. При совпадении **новый факт не создаётся**.
  3. Детерминированно инкрементируется `reinforcement_count`, обновляется `last_seen_at` и в массив `lineage` дописывается текущий `message_id`.
  4. Затраты LLM: **0** на этапе дедупликации.

### 4.2. Slow Path (Dreaming): Замещение и версионирование (**Р6, SCD Type 2**)
- **Проблема аналогов:** деструктивный `UPDATE`/`DELETE` затирает историю (Mem0), либо штраф на старые факты ломает контекст рассуждений (HippoGraph).
- **Решение Gestalt:**
  - При смене факта (например, миграция: *«Перешли с Java 21 на Java 25»*):
    1. У старого факта закрывается интервал: `valid_time.t_end = now()`.
    2. Статус старого факта меняется: `status = SUPERSEDED`, `superseded_by_id = new_fact.id`.
    3. Создаётся новый факт со статусом `ACTIVE` и `valid_time.t_start = now()`.
  - **Инвариант:** Старый факт остаётся в БД. Он исключается из базового скоупа актуальности, но доступен для исторического retrieval (*«на чём мы писали до марта 2026?»*).

### 4.3. Фоновое обобщение (Generalization во «сне», **13 §2**)
- Россыпь однородных микро-фактов (*«добавлен AssertJ»*, *«настроен Testcontainers»*, *«используется JUnit 5»*) в ходе процесса Dreaming кластеризуется и синтезируется в сводный факт уровня архитектуры:
  $$\text{Statement: «Стек модульного и интеграционного тестирования: JUnit 5, AssertJ, Testcontainers»}$$
- Первичные атомарные факты получают статус `RETIRED` (или понижаются в приоритете), предотвращая засорение контекста фрагментами.

### 4.4. Затухание без стирания: Forgetting curve / Decay-as-ranking-bias (**Н10(д)**)
- Факты не удаляются физически (деструктивное забывание отвергнуто каноном, `06 §8.1`).
- Для второстепенных фактов вычисляется коэффициент свежести на базе кривой Эббингауза:
  $$\text{decay}(t) = \max\left(0.3,\, \exp\left(-\frac{t - \text{last\_seen\_at}}{\tau}\right)\right)$$
- Множитель `decay` влияет **только на ранжирование при поиске** (ranking bias), но не стирает данные из базы.
- **Иммунитет от затухания:** факты с `permanence = USER_ASSERTED` или `is_critical = true` имеют $\text{decay} \equiv 1.0$ всегда.

## 5. Двухуровневая модель доставки в контекст

Мы никогда не подсовываем «1000 фактов» в диалог. Поставка знаний разделена на два непересекающихся контура:

```
┌────────────────────────────────────────────────────────────────────────┐
│ КОНТУР 1. СТАРТ СЕССИИ (Proactive Base, O(1), 0 LLM)                   │
│                                                                        │
│ PortraitSnapshot (лимит: ≤40 строк, ~2-4k символов)                    │
│ ┌────────────────────────────────────────────────────────────────────┐ │
│ │ [CRITICAL]    Жесткие инварианты мира (Java 21 LTS, Pure Postgres) │ │
│ ├────────────────────────────────────────────────────────────────────┤ │
│ │ [CONSTRUCTS]  Активные оси Келли (почерк инженера: PSYCHE)         │ │
│ ├────────────────────────────────────────────────────────────────────┤ │
│ │ [PREFERENCES] Стабильные предпочтения                              │ │
│ └────────────────────────────────────────────────────────────────────┘ │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ КОНТУР 2. ХОД ДИАЛОГА (Reactive Recall, On-demand, по запросу)         │
│                                                                        │
│ WORLD-Recall (лимит: Top 3-5 фактов, ≤500 токенов)                     │
│ ├── 1. Проектный барьер: WHERE project_id = :curr OR scope = 'USER'   │
│ ├── 2. Мультисигнальный поиск: RRF(pgvector, tsvector)                 │
│ ├── 3. Ранжирование: Score = Sim × Decay × log(Reinforcement)          │
│ └── 4. Инвариант No-False-Memory (Р14): тишина, если Score < Порог     │
└────────────────────────────────────────────────────────────────────────┘
```

### 5.1 Контур 1: Проактивный старт сессии (`PortraitSnapshot`, **Р19**)
- **Латентность:** $O(1)$, ~2 мс (готовый текстовый блок, материализованный в PG фоновым Reconciler).
- **Секция CRITICAL:** санкционированное `WORLD`-вкрапление (`14 §2`).
  - В секцию отбираются факты `WORLD`, удовлетворяющие предикату:
    $$\text{status} = \text{ACTIVE} \;\land\; \text{is\_critical} = \text{true} \;\land\; (\text{project\_id} = S.\text{project} \;\lor\; \text{scope} = \text{USER})$$
  - Примеры: архитектурные табу, выбранный стек, корневые ограничения (*«Java 21 LTS, Pure Postgres 16, Spring Boot запрещён»*).
  - **Бюджет:** не более 5–10 строк. Второстепенные факты сюда **не имеют права попасть**.

### 5.2 Контур 2: Реактивный `WORLD-Recall` во время общения в чате (**Н5**)
Срабатывает per-turn только при наличии предметного вопроса пользователя.

1. **Проектная изоляция (10 §3.3):**
   Запрос видит только факты текущего проекта и глобальные факты пользователя:
   ```sql
   WHERE status = 'ACTIVE' 
     AND owner_id = :user_id 
     AND (project_id = :current_project_id OR scope = 'USER')
   ```
   Факты соседних проектов (например, Java 11 из `legacy-service`) физически отсекаются на уровне SQL-фильтра.
2. **Мультисигнальный поиск (Multi-signal retrieval):**
   Объединение результатов семантического векторного поиска и точного текстового поиска через Reciprocal Rank Fusion (RRF):
   $$\text{RRF\_Score}(d) = \frac{1}{k + \text{rank}_{dense}(d)} + \frac{1}{k + \text{rank}_{sparse}(d)}$$
3. **Финальный ранг с учётом затухания и надёжности:**
   $$\text{Final\_Score}(d) = \text{RRF\_Score}(d) \times \text{decay}(d) \times \left(1 + 0.2 \cdot \ln(1 + \text{reinforcement\_count})\right)$$
4. **Строгий кап (Top-K budget):**
   В контекст передаётся строго **Top 3–5 фактов** (не более 300–500 токенов).
5. **Инвариант No-False-Memory (Р14):**
   Если максимальный `Final_Score` кандидатов ниже установленного порога отсечения $T_{\text{relevance}}$, память возвращает **пустой список**. Агент не должен галлюцинировать или притягивать факты не по теме (урок NGT/DRM-парадигмы: лучше промолчать, чем вставить неуместный факт).

## 6. Сопряжение доменов: как `WORLD` связан с `PSYCHE`

Между семантической памятью (`WORLD`) и моделью личности Келли (`PSYCHE`) действует строгий **инвариант чистоты и «одна дверь»** (`10 §4`):

```
                      ┌────────────────────────┐
                      │      Fact / WORLD      │
                      │ (Java 21, Linux, jOOQ) │
                      └───────────┬────────────┘
                                  │
                 ┌────────────────┴────────────────┐
                 │                                 │
     [Как объект в conditions]         [Сырьё для индукции]
                 │                                 │
                 ▼                                 ▼
      ConstructInstance.conditions        Gestalting (медленный сон)
    «Новизна [в pet-проектах]»                     │
    «Стабильность [в enterprise]»                  ▼
                 │                       Вывод мета-концепта:
                 │                       «Широкий кругозор: ведёт
                 │                       legacy и modern параллельно»
                 ▼                                 │
    ┌─────────────────────────┐                    ▼
    │     PortraitSnapshot    │◄───────────────────┘
    └─────────────────────────┘
```

1. **Инвариант чистоты:** факт `WORLD` напрямую никогда не становится осью или инстансом конструкта личности.
2. **Использование в `conditions` конструктов:** факты мира служат контекстными ограничителями для осей Келли (`09 §3`). Инженер не «вообще консервативен» — он консервативен применительно к `legacy-service` (`conditions: legacy, production`) и радикально открыт новому в личных разработках (`conditions: pet-project, experimental`).
3. **Кросс-проектная индукция во сне (`Gestalting`, 13 §2):**
   Совокупность разнородных проектных фактов (ведёт сервис на Java 11 и проект на Java 21) во время `Gestalting` индуцирует личностное мета-знание о высокой профессиональной гибкости и переключаемости стилей инженера.
