## 1. Постановка

Пример: юзер ведёт рабочий проект legacy-service на Java 11 и проект gestalt на Java 21.

- факты «проект на Java 11» / «проект на Java 21» релевантны каждый только в своём проекте;
- должны ли они участвовать в психопортрете? Напрямую — нет (это про мир, не про психику), но их
  совокупность — знание о юзере (кругозор: параллельно ведёт legacy и modern стек);
- запрос памяти с указанием проекта должен видеть: данные этого проекта + глобальные данные юзера.

Из этого следуют три решения: контейнер Project, радиус применимости факта, дверь кросс-проектной индукции.

## 2. Триаж противоречий: conditions vs дрейф vs contradiction (уточнение к 09 §4)

Противоречащий факт разрешается по тому, **по чему кластеризуются противоречия**:

| Кластеризация | Диагноз | Механика | Теория |
|---|---|---|---|
| по контексту (одновременные, разные домены) | уточнение `conditions` | Instance расщепляется с разными conditions; конструкт не ошибочен, а шире реальности | мягкая аккомодация |
| по времени (контекст тот же, эпоха другая) | дрейф | старый valid_time-интервал закрывается, новый открывается; сдвиг = first-class факт | аккомодация-перестройка |
| ни по чему (один период, один контекст) | Contradiction | первоклассная запись, вес по recency + независимости observers, без усреднения | конфликт фактов |

Примеры (ось «стабильность ↔ новизна»):

- уточнение: «не трогай Java 11 в legacy-service» (работа) + «в gestalt сразу взял 21 и preview» (личное)
  → «стабильность [рабочие проекты]» + «новизна [личные]» — портрет точнее: стратегия переключается по домену;
- дрейф: в 2025 «ждёт, пока фича выйдет из preview», в 2026 «сам первым предлагает миграцию»
  (контекст тот же) → интервалы [2025: стабильность] → [2026: новизна], сдвиг = факт;
- contradiction: «любит детальные ревью» vs «просит только по делу» в один период и контекст.

## 3. Модель

### 3.1. Владение факта: owner + domain + scope

Иерархия v1: `User → Project → Session → Message` (workspace исключён — §6, Р11).

`Session.project_id` — **nullable** (решено 2026-09-03, вариант А): диалоги вне проектов честно
безпроектны; фиктивный синглтон-проект («common») отвергнут — псевдосущность, паттерн Р11
(«сущность раньше концепции»). Цена NULL-веток в запросах принята — это один предикат
в `context(S)` (§3.3).

Факт = **owner + domain + scope** — три независимых измерения (Р13):

- `owner` — всегда юзер: наследуется из сессии, из которой факт извлечён
  (Message ∈ Session ∈ Project ∈ User). «Абстрактных» фактов вне юзера не существует.
- `domain ∈ {WORLD, PSYCHE}` — **о чём** факт: предметная область, онтологическая категория
  (07). Определяет попадание в портрет (инвариант чистоты, §4) и дефолт scope (§3.2).
  Граница — **вид знания, не объект**: инференс о личности (черты, конструкты, предпочтения —
  выведенное наблюдателем) = PSYCHE; наблюдаемое о мире, включая юзера как объект мира
  (биография, состояние, действия, договорённости, проекты) = WORLD. «О человеке» ≠ «PSYCHE»:
  «переехал в SF», «аллергик» — WORLD.
- `scope ∈ {SESSION, PROJECT, USER}` — радиус релевантности **внутри владельца** — «**докуда**»
  (v1; WORKSPACE убран до возврата сущности по триггерам §6).

Scope — enum-атрибут записи факта, не сущность; lineage независимо указывает на исходные
Message/Session («**откуда**»). Радиус — не место хранения и не мера доверия (§3.4, правило 3).
Полная модель хранения, жизненный цикл и структура сущности Fact канонизированы в `16 - Fact и домен WORLD (семантическая память).md`.

Миграция: в структуре пилотных данных проекты закодированы в именах сессий → адаптер выводит Project из session-имён;
сессии без маркера — безпроектные (`project_id = NULL`, §3.1).

### 3.2. Дефолты scope по содержанию

| Domain факта (о чём) | Дефолт scope |
|---|---|
| WORLD, проектная сессия | `PROJECT` (проект owner-юзера) |
| WORLD, безпроектная сессия | `USER` (безпроектность — §3.1) |
| PSYCHE | `USER` — личность сквознит через проекты; `conditions` сужают («осторожен [в legacy-service]») |
| эфемерное / working memory («в этом чате условились N») | `SESSION` — session purity (обобщение Honcho-паттерна, Р10) |

Экстрактор судит о **содержании** факта, не о своей уверенности: недоверие живёт в
confidence/evidence (счётчик Р10, lineage≥2), не в радиусе.

### 3.3. Матрица видимости

| Факт \ Где читаем | своя сессия | чужая сессия того же проекта | сессии других проектов юзера |
|---|---|---|---|
| `SESSION` | ✅ пока сессия жива | ❌ | ❌ |
| `PROJECT` | ✅ | ✅ | ❌ |
| `USER` | ✅ | ✅ | ✅ |

```
context(S) = SESSION-факты {origin = S, сессия жива}
           ∪ PROJECT-факты {project = S.project}    // если сессия проектная
           ∪ USER-факты   {owner = S.user}
```

Проект — фильтр **релевантности**, не изоляции: соседний проект не секретен, а нерелевантен.
Явный запрос по чужому проекту или по эпизодике — отдельный read-режим (детали API — Н5/Н8).

Вклад чужих сессий виден опосредованно: их SESSION-факты напрямую скрыты, но лифтнутое Dreaming
уже живёт как PROJECT/USER-факт.

### 3.4. Жизненный цикл факта

```
Message (юзер U, сессия S, [проект P])
   │  ① рождение — fast path (экстракция, секунды): scope по содержанию (§3.2), lineage
   ▼
Fact { owner, scope, confidence, lineage }
   │  ② жизнь — read: видимость по §3.3; confidence растёт от повторов (независимо от scope)
    │  ③ лифт — slow path (Dreaming, часы): ко-подтверждение в независимой сессии
   ▼           → SESSION→PROJECT, PROJECT→USER (одна дверь, lineage на источники)
④ смерть: SESSION гаснет с сессией (soft; lineage вечен) ИЛИ retire / kill-insight (любой scope)
```

Правила (session purity в здоровом виде):

1. **SESSION — исключение, не дефолт**: только по сути временные факты. Широкое применение =
   голодание консолидации + нарушение Р8 (новые сессии вслепую, ре-экстракция).
2. **Лифт однонаправленный, только через ко-подтверждение**: повтор в независимой сессии — сильно;
   в независимом проекте — сильнейший evidence. Понижений scope нет — только смерть.
3. **scope ≠ confidence**: радиус — релевантность («где уместен»), счётчик/lineage — доверие
   («насколько верим»). Оси не смешивать.

Пример лифта: «в этом чате звать компонент reconciler» (S1, SESSION) → в S2 повторено независимо →
сон сопоставил → SESSION→PROJECT, lineage=[S1, S2] → термин проекта.

### 3.5. Смерть сессии: TTL-предикат + reconciler

Хост не обязан присылать close (терминал закрылся, процесс убился). Поэтому «сессия жива» —
вычислимый предикат, а не хранимый флаг:

```
is_active(session) = last_message_at > now() − TTL
```

- reconciler (self-healing свипер, Р10: lease + backoff + poison) **материализует** смерть:
  проставляет `closed_at` протухшим;
- закрытие = хук для Dreaming: пост-мортем «сон» по сессии — сон обрабатывает эпизоды **закрытого**
  дня; лифтить из живой сессии нельзя (следующее сообщение может противоречить);
- явный close от хоста — подсказка (ускоряет расписание), TTL — страховка от молчаливых хостов;
- **revival автоматический**: новое сообщение двигает `last_message_at` → сессия снова жива,
  её SESSION-факты снова в контексте; зомби-проблемы нет;
- смерть **soft**: SESSION-факт выпадает из контекст-сборки, но остаётся в БД как lineage;
- **Messages (эпизодика) не умирают никогда**: «что обсуждали в том чате» — отдельный
  эпизодический read-режим по логу сообщений (Тульвинг: эпизодика ≠ семантика);
- величина TTL — иерархический конфиг со снимком (Р10), не концепция.

## 4. Инвариант чистоты + одна дверь

Инвариант чистоты (в уточнённой формулировке, Р32): **индукция PSYCHE читает только PSYCHE-evidence** — оси и инстансы не выводятся из WORLD-фактов (контаминация «проект на Java 11» → «юзер консервативен» запрещена). Слепок при этом шире портрета: CRITICAL — санкционированное WORLD-вкрапление (`14 §2`, исключение мотивировано уроком NGT); в индукцию WORLD не попадает и там используется только как объекты `conditions` (§5).

Дверь: кросс-проектная индукция — **два исполнения по слоям** (Р33):

- компетенсные (subject=user, WORLD): «ведёт legacy 11 и modern 21 параллельно» — кругозор; консолидация фактов → **Dreaming** (ко-подтверждение + лифт scope, lineage на исходники);
- поведенческие PSYCHE: «быстро осваивает новые версии» — инференс → **Gestalting** (единственный владелец смыслового слоя, 13 §2);
- ко-подтверждение из **независимых проектов** — сильнейший вид evidence (сильнее двух фактов одного проекта).

## 5. Семантика запроса

`read(user, project P)`:

- WORLD: `scope ∈ {PROJECT=P, USER}`;
- PSYCHE: глобальные + Instance, чьи `conditions` матчат P.

Проект — фильтр **релевантности**, не изоляции: RLS — по `user_id` (Р11);
соседний проект не секретен, а нерелевантен.

## 6. Workspace: исключён из v1 (решение сессии, Р11)

Договорились (2026-09-03): **в v1 сущности Workspace нет**. Иерархия `User → Project → Session → Message`;
изоляция — RLS по `user_id`; tenant = сам деплой. Внешние тенант-идентификаторы при импорте сворачиваются в метку
провенанса (data-compat по Р15 — совместимость по данным, не по схеме).

Обоснование: YAGNI (в personal-деплое workspace≈user — синглтон, мёртвый груз в каждой таблице и запросе);
роли воркспейса (изоляция/деплой/соцединица/контекст) не согласованы — сущность раньше концепции;
SaaS-модели внешних систем («изоляция как фундамент») — дефект для личного/командного деплоя. Workspace нигде явно не решался
для v1 — в ранних набросках присутствовал по инерции внешних аналогов.

Триггеры введения (v2/v3) — сущность возвращается, когда сработает любой:

- hosted multi-tenant SaaS (один инстанс — много чужих клиентов);
- командные проекты / UU-квадрант (проект перестаёт принадлежать одному User);
- AA-квадрант с портретами агентов в собственности тенанта;
- billing/квоты как граница.

Ввод — аддитивной миграцией (tenant-колонка + backfill); API v1 не закладывает workspace в пути.
